# 0040 ユーザーに見せる言葉を整理する。表では「タスク索引」と呼び、索引の 1 項目を「タスク」と呼ぶ

- 状態: 案（2026-11-08、直樹の指摘から。同日に直樹の方向で 2 回書き直した: 「タスク索引」とスキル名 `heddleway:task-index`、スタンドは「エージェント」、仕分け待ちは「割当待ち」、名指しは「アテンション」で押し切る。残る大きな論点は決定 2 の「タスク」の固定）。採用したら、スキル・ゲートウェイの画面・プラグインの説明・`README.md`・`CLAUDE.md` を直す。過去の ADR は書き換えない
- 関連: 0005（Murmur はゲートウェイの機能。「チームの仕事の記憶」）、0010（黒子）、0012（抽出と追跡）、0014（スレッド 1 種類。データソースの写し）、0023（ゲートウェイの機能）、0032（エージェントの参加）、0035（状態を持つソースのアクションの範囲）、0038（担当と名指し。この ADR で表の言葉を改める）、0039（言葉の節。タスク・メモ・操作。この ADR で表の「タスク」の意味を改める）、H9

## 背景

スキル（`plugins/heddleway/skills/murmur/SKILL.md`）を読んだときに、言葉が分かりにくい（2026-11-08、直樹）。

1. **「Murmur」という名前が唐突**: スキルの説明は「連絡の索引「Murmur」(プロトタイプ)」で始まり、本文にも 35 回出る。Heddleway の機能の 1 つ（0005・0023）なのに、別の製品のように見え、名前から何をするものかが想像できない。説明も揃っていない（スキルは「連絡の索引」、プラグインと `README.md` は「チームの仕事の記憶」）。ゲートウェイの画面とサービスの表示名（`display_name`）にも「Murmur」と出る
2. **「名指し」が分かりにくい**: 0038 の言葉で、スキルに 29 回出る。日常の「名指し」は「特に名前を挙げて指す（多くは非難）」の意味で、「宛先に入っていて、外すまで残るもの」と結びつかない
3. **「タスク」と「スレッド」が 2 つの言葉になっている**: Heddleway の中では、索引の 1 項目（スレッド。0014 のエンティティ 1 種類）がそのまま「やること」の単位で、同じものを指す。一方、スキルの「タスク」は To Do のタスクだけ（0039）で、85 回出る。「スレッド」はメールや Slack のスレッドを思わせ、Jira の課題や To Do のタスクを指すと分かりにくい
4. **ほかにも内側の言葉がそのまま出ている**: スタンド・読者・名乗る・シグナル・綴じる・ゴースト・データソースとリストの 2 語・開き直し（日常の意味は「居直る」）・相手待ちと返事待ちの 2 語など

言葉には 2 つの層がある。

- **内側の言葉**: ADR・コード・API の名前（`murmur`・`identity:murmur`・`thread`・`attention`・`acknowledge`・`ThreadClaimed`・`data_source` など）。設計の議論で使い、変えるとコストが大きい
- **表の言葉**: ユーザーが目にする言葉と、エージェントがユーザーに話す言葉。スキルの説明と本文、ゲートウェイの画面、サービスの表示名、プラグインの説明、`README.md`

今は内側の言葉がそのまま表に出ている。この ADR は表の言葉だけを決める。

## 決定（案）

### 1. 表では「タスク索引」と呼ぶ。スキルは `heddleway:task-index`

- Murmur の本質は**タスクの索引**。タスクの中身は持たず（中身はメール・Jira の課題・To Do などのソースにある。0010・0014）、どこにどんなタスクがあり、誰の番かを引けるようにする。本の索引がページを指すのと同じで、管理はしない（`CLAUDE.md` の「タスク管理ツールではない」と合う）
- 表に出す機能名は「**タスク索引**」（Heddleway の機能）。「チームの仕事の記憶」「連絡の索引」はやめる
- スキルの名前を `heddleway:task-index` にする（ディレクトリ `plugins/heddleway/skills/task-index/`）。ほかのスキルからの参照（`microsoft-graph` の `references/todo.md` の「`murmur` スキル」）も直す
- サービスの表示名（`display_name`）とゲートウェイの画面: 「タスク索引」。有効にする画面は「タスク索引を有効にしますか?」に、何を読むか（読むだけで書かない）の 1 行を添える
- 内側では Murmur のまま: ディレクトリ `murmur/`、上流のサービス名 `murmur`、`identity:murmur`、API のパス、ADR、コード。スキルの本文で `murmur` と書くのは、この名前が要るところ（`gw_request.py ... murmur /threads`、`identity:murmur`）だけ

### 2. 索引の 1 項目を「タスク」と呼ぶ。「スレッド」は表に出さない

内側のスレッド（`thread`）と表のタスクを 1 対 1 にする。

| 表の言葉 | 意味 | 内側 |
| --- | --- | --- |
| **タスク** | 索引の 1 項目。ソース（メール・Teams の投稿・Jira の課題・To Do のタスクなど）から写したもので、メッセージ・メモ・操作が時刻順に並ぶ | スレッド（`thread`・`thread_id`） |
| **ソース** | タスクの元（どのリストの、どのメール・投稿・課題か） | データソースとアンカー |
| **To Do のタスク** | ソースが To Do（将来 Google Tasks）のタスク。To Do の側で作る・期限を変える・完了にする | チャネル `todo` のスレッド |
| **自分の番** | 担当が自分か、自分へのアテンションが残っているタスク | `my_turn` |

- 「タスク索引のタスク」で名前と中身が一致する。0038 の「担当: このタスクを進める人」も、もともとこの意味で「タスク」を使っている
- 0039 の「タスク」（着手を決めて追うもの = To Do のタスク）は、表では「To Do のタスク」と呼ぶ。スキルの「タスクとして追う」は「**To Do のタスクで追う**」（自分の To Do に作り、関係するタスクと結ぶ）にする

ためした読み替え（スキルの今の文で、破綻がないかを見た）:

| 今の文 | 書き換え | 読み |
| --- | --- | --- |
| 自分の番のスレッドを見せる | 自分の番のタスクを見せる | 自然 |
| スレッドの経過とタイムライン | タスクの経過 | 自然 |
| シグナルを別のスレッドへ移す（振り分けの直し） | メッセージを別のタスクへ移す | 自然 |
| スレッド同士を結ぶ | タスク同士を結ぶ | 自然 |
| 共有のスレッドには進み具合を書かない | 共有リストのタスクには進み具合を書かない | 自然 |
| 1 つのタスクが複数のスレッドにまたがれば結ぶ | 1 つの To Do のタスクに、関係するタスク（課題・メール）を結ぶ | タスクがタスクを束ねる形になる。親子ではなく対等なリンクだと 1 行書く |
| タスクを作るまでもなければ、Outlook のスレッドにメモ | To Do に作るまでもなければ、メールのタスクにそのままメモ | 自然 |
| 個人の Outlook の FYI のメール | 誰の番でもないタスク | **引っかかる点**: ニュースレターのようなメールもタスクになる。「取り込んだものは全部タスクになる。自分の番でなければ一覧（自分の番）には出ない」と書いて受け入れる |
| フラグを付けたメール（To Do の `flaggedEmails`） | メールのタスクと To Do のタスクの 2 つ | 今も 2 つのスレッド。結べばよい |

- 「この件」「用件」は 0039 のとおり言葉として使わない（ユーザーの話し言葉の例は別）
- ほかの候補: 「項目」（意味が薄い）、「案件」（販売管理の案件とぶつかる）、「チケット」（Jira の言葉）、「やりとり」（To Do のタスクに合わない）、「スレッド」のまま（背景の 3）

### 3. 「名指し」は表では「アテンション」と呼ぶ

| 内側（0038・API） | 表の言葉 |
| --- | --- |
| 名指し（`attention`） | **アテンション**（宛先から溜まり、外すまで残る「少なくとも見てほしい」の印） |
| `attention.named` | 自分へのアテンション／相手へのアテンション（メンバーでない相手） |
| `attention.list` | リスト宛てのアテンション |
| 名指しを外す（`acknowledge`） | **アテンションを外す**（読んで、対応が要るか FYI かを決めた） |
| `myTurn` の理由 `assignee` / `named` / `list` | 担当 / アテンション / リスト宛て |

- ベストではないが、当てはまる既存の日本語の概念が少ない。API の `attention` と同じ言葉で、エージェントが API の結果とユーザーへの説明を行き来しやすく、ほかの言葉ともぶつからない。これで押し切る
- 「外す」は既読ではない。ソースの既読・未読とは連動しない（0038 の決定 3）。スキルにそう 1 行書く
- 検討した言葉: 「宛て」（名詞の「宛てが残る」「宛てを外す」が不自然）、「確認待ち」（相手の側で主語がずれ、「ユーザーに確かめる」の「確認」とぶつかる）、「メンション」（メールの To・CC に合わない）、「未読」（ソースの既読と混ざる）

### 4. ほかの言葉もまとめて表の言葉にする

| 今の言葉 | 表の言葉 | 備考 |
| --- | --- | --- |
| スタンド | **エージェント**（スキルの中では「あなた」） | Heddleway はエージェント中立（Claude に限らない）。0032 の参加するエージェント（`author.kind: "agent"`）と同じ言葉になるが、どちらも「ユーザーの代わりにタスク索引を使うもの」で食い違わない。内側では 0010 のまま |
| 読者 | **メンバー**（リストのメンバー） | コードの `ListMember` と合う。「読者でない相手」→「メンバーでない相手（お客さんなど）」 |
| 名乗る | 自分のアカウントを登録する | |
| シグナル | **メッセージ**（メール 1 通・投稿 1 つ・コメント 1 つ） | |
| 綴じる | 入れる・まとめる | |
| データソース | **リスト** | データソースごとに 1 つのリストなので 1 語にする。API の `data_source`・`list_id` はそのまま |
| ゴースト | 仮の連絡先（まだ本人が登録していない連絡先） | |
| Contact | 連絡先 | |
| 個人の箱 | 自分のメールボックス・自分のアカウント | |
| 持つ（`claim`） | 担当する | 「持つ」と「担当する」の 2 語を 1 つにする |
| 仕分け待ち（`triage`） | **割当待ち** | 共有リストで担当が決まっていないタスク |
| 相手待ち・返事待ち（`awaiting`） | **返事待ち** | 2 語を 1 つにする |
| 返事期待（`reply_expected_by`） | 返事の期限 | |
| 開き直し（`reopen`） | **再開する** | 「開き直る」は日常では「居直る」の意味 |
| 結び候補 | 結ぶ候補 | |
| 経路（リンクの `sent` / `anchor` / `manual`） | 結んだきっかけ | |
| `derivedBall` | 結んだ先から見た番 | 0038 でボールはやめた |

そのまま使う言葉: リスト（個人リスト・共有リスト）、担当、メモ、片付ける、結ぶ、写し、名寄せ、期限超過、自分の番。

### 5. スキルの冒頭に言葉の対応表を置く

- スキルの冒頭に「言葉」の節を置き、表の言葉・意味・API の名前の対応表を書く（決定 2〜4 の表をまとめたもの）。特に「タスク = API の `thread`」を最初に書く
- エージェントは、ユーザーに話すときは表の言葉を使う。API の名前（`thread`・`my_turn`・`acknowledge` など）は、ユーザーが聞いたときだけ出す

### 6. 直す範囲

- 直す: スキル（`murmur` → `task-index`。本文の言葉）、`microsoft-graph` の `references/todo.md`、プラグインの説明（`plugin.json`・`marketplace.json`）、ゲートウェイの画面（`src/web/`）、サービスの表示名（`display_name`。`README.md` の例も）、`README.md` の Murmur の節、`murmur/CLAUDE.md`（表の言葉と内側の言葉の対応を足す）
- 直さない: 過去の ADR（経緯の記録）、コードの識別子、API、イベントの名前。コードのコメント・テスト名の「名指し」「読者」「スレッド」は内側の言葉として残してよい（直すなら別の PR）
- スキルの名前が変わるので、`heddleway` プラグインの版を上げる（マイナー）。導入済みの環境では、プラグインを更新すると `murmur` スキルが `task-index` に入れ替わる
- プラグインはまだ Claude 向けだけ（ChatGPT などには未対応）。スキルの本文はエージェント中立の言葉で書き、Claude 固有のこと（`${CLAUDE_SKILL_DIR}` など）は手順の中に閉じ込める

## 未決

1. **決定 2（タスク = スレッド）でよいか**: 最大の論点。取り込んだメールが全部「タスク」になる点（決定 2 の表の引っかかる点）を受け入れられるか
2. **ゲートウェイの画面の言葉**: 「タスク索引を有効にしますか?」で、初めて見る人に何が起きるか伝わるか。添える 1 行の文面は実装のときに見てもらう

## 代案

- **Murmur の名前を表でも使い、説明を足す**: 名前から中身が想像できない問題は残る。複数の組織の Heddleway につないでいるとき、「どの組織のタスク索引か」のほうが自然
- **表でも「スレッド」を使い、「タスク」を To Do のものに限る**: 「タスク索引」の大半（メール・課題）が「タスクではない」ことになり、名前と中身が合わない
- **内側の言葉も含めて全部改名する**（`thread` → `task`、`signal` → `message` など）: 一貫するが、API・イベント・投影・テスト・ADR の言い換えが大きい。表の言葉が落ち着いてから考えればよい
