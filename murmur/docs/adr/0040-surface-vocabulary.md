# 0040 ユーザーに見せる言葉を整理する。表では「タスク索引」と呼び、スキルは `heddleway:task-index` にする

- 状態: 案（2026-11-08、直樹の指摘から。同日に「タスク索引」「アテンション」の方向をもらって書き直した）。採用したら、スキル・ゲートウェイの画面・プラグインの説明・`README.md`・`CLAUDE.md` を直す。過去の ADR は書き換えない
- 関連: 0005（Murmur はゲートウェイの機能。「チームの仕事の記憶」）、0010（黒子）、0012（抽出と追跡）、0014（スレッド 1 種類。データソースの写し）、0023（ゲートウェイの機能）、0035（状態を持つソースのアクションの範囲）、0038（担当と名指し。この ADR で表の言葉を改める）、0039（言葉の節。タスク・メモ・操作。この ADR で「タスク」の意味を広げる）、H9

## 背景

スキル（`plugins/heddleway/skills/murmur/SKILL.md`）を読んだときに、言葉が分かりにくい（2026-11-08、直樹）。

1. **「Murmur」という名前が唐突**: スキルの説明は「連絡の索引「Murmur」(プロトタイプ)」で始まり、本文にも 35 回出る。Heddleway の機能の 1 つ（0005・0023）なのに、別の製品のように見え、名前から何をするものかが想像できない。説明も揃っていない（スキルは「連絡の索引」、プラグインと `README.md` は「チームの仕事の記憶」）。ゲートウェイの画面とサービスの表示名（`display_name`）にも「Murmur」と出る
2. **「名指し」が分かりにくい**: 0038 の言葉で、スキルに 29 回出る。日常の「名指し」は「特に名前を挙げて指す（多くは非難）」の意味で、「宛先に入っていて、外すまで残るもの」と結びつかない。「名指しを外す」も何をする操作かが読み取れない
3. **ほかにも内側の言葉がそのまま出ている**: スタンド・読者・名乗る・シグナル・綴じる・ゴースト・データソースとリストの 2 語・開き直し（日常の意味は「居直る」）・相手待ちと返事待ちの 2 語など

言葉には 2 つの層がある。

- **内側の言葉**: ADR・コード・API の名前（`murmur`・`identity:murmur`・`attention`・`acknowledge`・`ThreadClaimed`・`data_source` など）。設計の議論で使い、変えるとコストが大きい
- **表の言葉**: ユーザーが目にする言葉と、Claude がユーザーに話す言葉。スキルの説明と本文、ゲートウェイの画面、サービスの表示名、プラグインの説明、`README.md`

今は内側の言葉がそのまま表に出ている。この ADR は表の言葉だけを決める。

## 決定（案）

### 1. 表では「タスク索引」と呼ぶ。スキルは `heddleway:task-index`

- Murmur の本質は**タスクの索引**。タスクそのものは持たず（タスクは Jira の課題・To Do・返事の要るメールとして、それぞれのソースにある。0010・0014）、どこに自分のタスクがあり、誰の番かを引けるようにする。本の索引がページを指すのと同じで、管理はしない（`CLAUDE.md` の「タスク管理ツールではない」と合う）
- 表に出す機能名は「**タスク索引**」（Heddleway の機能）。「チームの仕事の記憶」「連絡の索引」はやめる
- スキルの名前を `heddleway:task-index` にする（ディレクトリ `plugins/heddleway/skills/task-index/`）。ほかのスキルからの参照（`microsoft-graph` の `references/todo.md` の「`murmur` スキル」）も直す
- サービスの表示名（`display_name`）とゲートウェイの画面: 「タスク索引」。有効にする画面は「タスク索引を有効にしますか?」に、何を読むか（読むだけで書かない）の 1 行を添える
- 内側では Murmur のまま: ディレクトリ `murmur/`、上流のサービス名 `murmur`、`identity:murmur`、API のパス、ADR、コード。スキルの本文で `murmur` と書くのは、この名前が要るところ（`gw_request.py ... murmur /threads`、`identity:murmur`）だけ

### 2. 「タスク」を「やること」の意味に広げ、To Do のものは「To Do のタスク」と呼ぶ

「タスク索引」と呼ぶと、今のスキルの「タスク」（0039 の言葉。To Do のタスクだけ）と食い違う。索引に入っているのに To Do のタスクでないもの（Jira の課題・メール）が「タスクではない」ように読める。そこで次のように分ける。

| 言葉 | 意味 |
| --- | --- |
| **タスク** | やること。担当が自分のもの（Jira の課題・`claim` したスレッド）、自分へのアテンションが残っているもの、To Do のタスク。「自分のタスク」= 自分の番（`my_turn`） |
| **To Do のタスク** | To Do（将来 Google Tasks）にあるタスク。0039 でいう「タスク」。`filter=mine` は「To Do のタスクの一覧」 |
| **スレッド** | 索引の 1 項目（連絡のまとまり。ソースの写し）。タスクでないもの（FYI のメール・文脈として入った課題）もある |

- 0038 の「担当: このタスクを進める人」は、すでに広い意味で「タスク」を使っている。広い意味に揃えると 0038 とも合う
- スキルの「タスクとして追う」は「**To Do のタスクで追う**」、「タスクのスレッド」は「To Do のタスクのスレッド」にする
- 「索引のスレッドのうちタスクでないもの」があるのは破綻ではない: 索引は文脈（0035 の「ほかは文脈として取り込む」）も含み、そこから自分のタスクを引く

### 3. 「名指し」は表では「アテンション」と呼ぶ

| 内側（0038・API） | 表の言葉 |
| --- | --- |
| 名指し（`attention`） | **アテンション**（宛先から溜まり、外すまで残る「少なくとも見てほしい」の印） |
| `attention.named` | 自分へのアテンション／相手へのアテンション（メンバーでない相手） |
| `attention.list` | リスト宛てのアテンション |
| 名指しを外す（`acknowledge`） | **アテンションを外す**（読んで、対応が要るか FYI かを決めた） |
| `myTurn` の理由 `assignee` / `named` / `list` | 担当 / アテンション / リスト宛て |

- API の `attention` と同じ言葉なので、Claude が API の結果とユーザーへの説明を行き来しやすい。ほかの言葉とぶつからない
- 「外す」は既読ではない。ソースの既読・未読とは連動しない（0038 の決定 3）。スキルにそう 1 行書く
- 検討した言葉:
  - 「宛て」: 「自分宛て」は自然だが、名詞として「宛てが残る」「宛てを外す」は日本語として不自然
  - 「確認待ち」（外すのは「確認済みにする」）: 自分の側は自然。相手の側の「相手の確認待ちを確認済みにする」で主語がずれる。「確認」はスキルの中で「ユーザーに確かめる」の意味でも多く出てぶつかる
  - 「メンション」: Teams・Slack の言葉で、メールの To・CC に合わない
  - 「未読」: ソースの既読と混ざる

### 4. ほかの言葉もまとめて表の言葉にする

| 今の言葉 | 表の言葉 | 備考 |
| --- | --- | --- |
| スタンド | Claude（スキルの中では「あなた」） | 内側では 0010 のまま |
| 読者 | **メンバー**（リストのメンバー） | コードの `ListMember` と合う。「読者でない相手」→「メンバーでない相手（お客さんなど）」 |
| 名乗る | 自分のアカウントを登録する | |
| シグナル | **メッセージ**（メール 1 通・投稿 1 つ・コメント 1 つ） | `move_signal` は「メッセージを別のスレッドへ移す」 |
| 綴じる | まとめる・入れる | |
| データソース | **リスト** | データソースごとに 1 つのリストなので 1 語にする。API の `data_source` はそのまま |
| ゴースト | 仮の連絡先（まだ本人が登録していない連絡先） | |
| Contact | 連絡先 | |
| 個人の箱 | 自分のメールボックス・自分のアカウント | |

| 仕分け待ち（`triage`） | **担当待ち** | 共有リストで担当のいないもの。何を待っているかが分かる |

そのまま使う言葉: スレッド、リスト（個人リスト・共有リスト）、担当、メモ、片付ける、結ぶ、写し、名寄せ、期限超過、自分の番。

### 5. スキルの冒頭に言葉の対応表を置く

- スキルの冒頭に「言葉」の節を置き、表の言葉・意味・API の名前の対応表を書く（決定 2〜4 の表をまとめたもの）
- Claude は、ユーザーに話すときは表の言葉を使う。API の名前（`my_turn`・`acknowledge` など）は、ユーザーが聞いたときだけ出す

### 6. 直す範囲

- 直す: スキル（`murmur` → `task-index`。本文の言葉）、`microsoft-graph` の `references/todo.md`、プラグインの説明（`plugin.json`・`marketplace.json`）、ゲートウェイの画面（`src/web/`）、サービスの表示名（`display_name`。`README.md` の例も）、`README.md` の Murmur の節、`murmur/CLAUDE.md`（表の言葉と内側の言葉の対応を足す）
- 直さない: 過去の ADR（経緯の記録）、コードの識別子、API、イベントの名前。コードのコメント・テスト名の「名指し」「読者」は内側の言葉として残してよい（直すなら別の PR）
- スキルの名前が変わるので、`heddleway` プラグインの版を上げる（マイナー）。導入済みの環境では、プラグインを更新すると `murmur` スキルが `task-index` に入れ替わる

## 未決

1. **「アテンション」でよいか**: カタカナで、IT に慣れていない人には意味が浮かびにくい。スキルの中で 1 回定義すれば Claude は正しく使えるので、ユーザーにはまず Claude が「確認してほしいと届いたもの」のように言い換えて見せれば足りる、と考える
2. **ゲートウェイの画面の言葉**: 「タスク索引を有効にしますか?」で、初めて見る人に何が起きるか伝わるか。添える 1 行の文面は実装のときに見てもらう
3. **データソース → リストの 1 語化**: スキルでは「データソース」と「リスト」がほぼ同じものを指している。API の名前（`data_source`・`list_id`）は 2 つ残るので、スキルの API の表では両方を出す

## 代案

- **Murmur の名前を表でも使い、説明を足す**: 名前から中身が想像できない問題は残る。複数の組織の Heddleway につないでいるとき、「どの組織のタスク索引か」のほうが自然
- **「タスク」を To Do のものに限ったまま「タスク索引」と呼ぶ**: 索引の大半（メール・課題）が「タスクではない」ことになり、名前と中身が合わない
- **内側の言葉も含めて全部改名する**（`attention` はそのまま、`signal` → `message` など）: 一貫するが、API・イベント・投影・テスト・ADR の言い換えが大きい。表の言葉が落ち着いてから考えればよい
