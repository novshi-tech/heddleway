# 0040 ユーザーに見せる言葉を整理する。表では「トピック索引」と呼び、索引の 1 項目を「トピック」と呼ぶ

- 状態: 採用（2026-11-08、直樹とのディスカッション。一度「タスク索引」・`heddleway:task-index` にしかけ、索引の 1 項目を「トピック」と呼ぶことにしたので揃えた。「トピック索引」とスキル名 `heddleway:topic-index`、索引の 1 項目は「トピック」、スタンドは「エージェント」、仕分け待ちは「割当待ち」、名指しは「アテンション」で押し切る）。同日にスキル・ゲートウェイの画面・プラグインの説明・`README.md`・`CLAUDE.md` を直した。過去の ADR は書き換えない
- 関連: 0005（Murmur はゲートウェイの機能。「チームの仕事の記憶」）、0010（黒子）、0012（抽出と追跡）、0014（スレッド 1 種類。データソースの写し）、0023（ゲートウェイの機能）、0032（エージェントの参加）、0035（状態を持つソースのアクションの範囲）、0038（担当と名指し。この ADR で表の言葉を改める）、0039（言葉の節。タスク・メモ・操作。この ADR で表の「タスク」の意味を改める）、H9

## 背景

スキル（`plugins/heddleway/skills/murmur/SKILL.md`）を読んだときに、言葉が分かりにくい（2026-11-08、直樹）。

1. **「Murmur」という名前が唐突**: スキルの説明は「連絡の索引「Murmur」(プロトタイプ)」で始まり、本文にも 35 回出る。Heddleway の機能の 1 つ（0005・0023）なのに、別の製品のように見え、名前から何をするものかが想像できない。説明も揃っていない（スキルは「連絡の索引」、プラグインと `README.md` は「チームの仕事の記憶」）。ゲートウェイの画面とサービスの表示名（`display_name`）にも「Murmur」と出る
2. **「名指し」が分かりにくい**: 0038 の言葉で、スキルに 29 回出る。日常の「名指し」は「特に名前を挙げて指す（多くは非難）」の意味で、「宛先に入っていて、外すまで残るもの」と結びつかない
3. **「タスク」と「スレッド」が 2 つの言葉になっている**: Heddleway の中では、索引の 1 項目（スレッド。0014 のエンティティ 1 種類）がそのまま「やること」の単位で、同じものを指す。一方、スキルの「タスク」は To Do のタスクだけ（0039）で、85 回出る。「スレッド」はメールや Slack のスレッドを思わせ、Jira の課題や To Do のタスクを指すと分かりにくい
4. **ほかにも内側の言葉がそのまま出ている**: スタンド・読者・名乗る・シグナル・綴じる・ゴースト・データソースとリストの 2 語・開き直し（日常の意味は「居直る」）・相手待ちと返事待ちの 2 語など

言葉には 2 つの層がある。

- **内側の言葉**: ADR・コード・API の名前（`murmur`・`identity:murmur`・`thread`・`attention`・`acknowledge`・`ThreadClaimed`・`data_source` など）。設計の議論で使い、変えるとコストが大きい
- **表の言葉**: ユーザーが目にする言葉と、エージェントがユーザーに話す言葉。スキルの説明と本文、ゲートウェイの画面、サービスの表示名、プラグインの説明、`README.md`

今は内側の言葉がそのまま表に出ている。この ADR は表の言葉だけを決める。

## 決定（案）

### 1. 表では「トピック索引」と呼ぶ。スキルは `heddleway:topic-index`

- Murmur の本質は、アクションアイテムの候補になる会話（トピック。決定 2）の**索引**。中身は持たず（中身はメール・Jira の課題・To Do などのソースにある。0010・0014）、トピックを索引にして、どこに自分のタスクがあり、誰の番かを引けるようにする。本の索引がページを指すのと同じで、管理はしない（`CLAUDE.md` の「タスク管理ツールではない」と合う）
- 表に出す機能名は「**トピック索引**」（Heddleway の機能）。「チームの仕事の記憶」「連絡の索引」はやめる
- スキルの名前を `heddleway:topic-index` にする（ディレクトリ `plugins/heddleway/skills/topic-index/`）。ほかのスキルからの参照（`microsoft-graph` の `references/todo.md` の「`murmur` スキル」）も直す
- サービスの表示名（`display_name`）とゲートウェイの画面: 「トピック索引」。有効にする画面は「トピック索引を有効にしますか?」に、何を読むか（読むだけで書かない）の 1 行を添える
- 内側では Murmur のまま: ディレクトリ `murmur/`、上流のサービス名 `murmur`、`identity:murmur`、API のパス、ADR、コード。スキルの本文で `murmur` と書くのは、この名前が要るところ（`gw_request.py ... murmur /threads`、`identity:murmur`）だけ

### 2. 索引の 1 項目を「トピック」と呼び、「タスク」は自分の番のトピックを指す。「スレッド」は表に出さない

索引に入るのは「アクションアイテムの候補になる会話」で、FYI のメールや Teams・Slack の雑談のように、タスクでないものも入る。そこで 2 段に分ける。

| 表の言葉 | 意味 | 内側 |
| --- | --- | --- |
| **トピック** | 索引の 1 項目。ソース（メールのやりとり・Teams の投稿・Jira の課題・To Do のタスクなど）から写したもので、メッセージ・メモ・操作が時刻順に並ぶ | スレッド（`thread`・`thread_id`） |
| **タスク**（自分のタスク） | トピックのうち、担当が自分か、自分へのアテンションが残っているもの。**自分の番のトピック** | `my_turn` |
| **ソース** | トピックの元（どのリストの、どのメール・投稿・課題か） | データソースとアンカー |
| **To Do のタスク** | ソースが To Do（将来 Google Tasks）のトピック。To Do の側で作る・期限を変える・完了にする | チャネル `todo` のスレッド |

- タスクは新しいエンティティではなく、0038 の「誰の番」（担当とアテンションから導く見え方）の名前。FYI のメールは、アテンションを外せばただのトピックに戻る
- 「トピック索引」は、トピックの索引から自分のタスク（自分の番のトピック）を引くもの。0038 の「担当: このタスクを進める人」とも合う
- 0039 の「タスク」（着手を決めて追うもの）は、表では「To Do のタスク」と呼ぶ。スキルの「タスクとして追う」は「**To Do のタスクで追う**」（自分の To Do に作り、関係するトピックと結ぶ）にする
- 話し言葉の「この件」は、エージェントがユーザーと話すときに使ってよい。用語としては固定しない（0039 のとおり「件」「用件」は言葉にしない）

ためした読み替え（スキルの今の文で、破綻がないかを見た）:

| 今の文 | 書き換え |
| --- | --- |
| 自分の番のスレッドを見せる | 自分のタスクを見せる |
| スレッドの経過とタイムライン | トピックの経過 |
| シグナルを別のスレッドへ移す（振り分けの直し） | メッセージを別のトピックへ移す |
| スレッド同士を結ぶ | トピック同士を結ぶ |
| 共有のスレッドには進み具合を書かない | 共有リストのトピックには進み具合を書かない |
| 1 つのタスクが複数のスレッドにまたがれば結ぶ | 1 つの To Do のタスクに、関係するトピック（課題・メール）を結ぶ |
| タスクを作るまでもなければ、Outlook のスレッドにメモ | To Do に作るまでもなければ、メールのトピックにそのままメモ |
| 仕分け待ちのスレッド | 割当待ちのトピック |

- 「Jira の課題のトピック」はくどいので、文脈で分かるときは「課題」と書く
- ほかの候補: 「件」（話し言葉では一番自然だが、「3 件」「件名」とまぎれる）、「話題」（「話題を結ぶ」が不自然）、「項目」（意味が薄い）、「タスク候補」（長く、To Do のタスクまで候補になる）、「タスク」（タスクでないものまでタスクと呼ぶことになる）、「スレッド」のまま（背景の 3）

### 3. 「名指し」は表では「アテンション」と呼ぶ

| 内側（0038・API） | 表の言葉 |
| --- | --- |
| 名指し（`attention`） | **アテンション**（宛先から溜まり、外すまで残る「少なくとも見てほしい」の印） |
| `attention.named` | 自分へのアテンション／相手へのアテンション（メンバーでない相手） |
| `attention.list` | リスト宛てのアテンション |
| 名指しを外す（`acknowledge`） | **アテンションを外す**（読んで、対応が要るか FYI かを決めた） |
| `myTurn` の理由 `assignee` / `named` / `list` | 担当 / アテンション / リスト宛て |

- ベストではないが、当てはまる既存の日本語の概念が少ない。API の `attention` と同じ言葉で、エージェントが API の結果とユーザーへの説明を行き来しやすく、ほかの言葉ともぶつからない。これで押し切る
- 「外す」は既読ではない。ソースの既読・未読とは連動しない（0038 の決定 3）。スキルにそう 1 行書く
- 検討した言葉: 「宛て」（名詞の「宛てが残る」「宛てを外す」が不自然）、「確認待ち」（相手の側で主語がずれ、「ユーザーに確かめる」の「確認」とぶつかる）、「メンション」（メールの To・CC に合わない）、「未読」（ソースの既読と混ざる）

### 4. ほかの言葉もまとめて表の言葉にする

| 今の言葉 | 表の言葉 | 備考 |
| --- | --- | --- |
| スタンド | **エージェント**（スキルの中では「あなた」） | Heddleway はエージェント中立（Claude に限らない）。0032 の参加するエージェント（`author.kind: "agent"`）と同じ言葉になるが、どちらも「ユーザーの代わりにトピック索引を使うもの」で食い違わない。内側では 0010 のまま |
| 読者 | **メンバー**（リストのメンバー） | コードの `ListMember` と合う。「読者でない相手」→「メンバーでない相手（お客さんなど）」 |
| 名乗る | 自分のアカウントを登録する | |
| シグナル | **メッセージ**（メール 1 通・投稿 1 つ・コメント 1 つ） | |
| 綴じる | 入れる・まとめる | |
| データソース | **リスト** | データソースごとに 1 つのリストなので 1 語にする。API の `data_source`・`list_id` はそのまま |
| ゴースト | 仮の連絡先（まだ本人が登録していない連絡先） | |
| Contact | 連絡先 | |
| 個人の箱 | 自分のメールボックス・自分のアカウント | |
| 持つ（`claim`） | 担当する | 「持つ」と「担当する」の 2 語を 1 つにする |
| 仕分け待ち（`triage`） | **割当待ち** | 共有リストで担当が決まっていないトピック |
| 相手待ち・返事待ち（`awaiting`） | **返事待ち** | 2 語を 1 つにする |
| 返事期待（`reply_expected_by`） | 返事の期限 | |
| 開き直し（`reopen`） | **再開する** | 「開き直る」は日常では「居直る」の意味 |
| 結び候補 | 結ぶ候補 | |
| 経路（リンクの `sent` / `anchor` / `manual`） | 結んだきっかけ | |
| `derivedBall` | 結んだ先から見た番 | 0038 でボールはやめた |

そのまま使う言葉: ソースの言葉（Jira の課題・To Do のタスク・メール・投稿）、リスト（個人リスト・共有リスト）、担当、メモ、片付ける、結ぶ、写し、名寄せ、期限超過、自分の番。

### 5. スキルの冒頭に言葉の対応表を置く

- スキルの冒頭に「言葉」の節を置き、表の言葉・意味・API の名前の対応表を書く（決定 2〜4 の表をまとめたもの）。特に「トピック = API の `thread`」「タスク = 自分の番のトピック（`my_turn`）」を最初に書く
- エージェントは、ユーザーに話すときは表の言葉を使う。API の名前（`thread`・`my_turn`・`acknowledge` など）は、ユーザーが聞いたときだけ出す

### 6. 直す範囲

- 直す: スキル（`murmur` → `topic-index`。本文の言葉）、`microsoft-graph` の `references/todo.md`、プラグインの説明（`plugin.json`・`marketplace.json`）、ゲートウェイの画面（`src/web/`）、サービスの表示名（`display_name`。`README.md` の例も）、`README.md` の Murmur の節、`murmur/CLAUDE.md`（表の言葉と内側の言葉の対応を足す）
- 直さない: 過去の ADR（経緯の記録）、コードの識別子、API、イベントの名前。コードのコメント・テスト名の「名指し」「読者」「スレッド」は内側の言葉として残してよい（直すなら別の PR）
- スキルの名前が変わるので、`heddleway` プラグインの版を上げる（マイナー）。導入済みの環境では、プラグインを更新すると `murmur` スキルが `topic-index` に入れ替わる
- プラグインはまだ Claude 向けだけ（ChatGPT などには未対応）。スキルの本文はエージェント中立の言葉で書き、Claude 固有のこと（`${CLAUDE_SKILL_DIR}` など）は手順の中に閉じ込める

## 未決

1. **ゲートウェイの画面の言葉**: 「トピック索引を有効にしますか?」に添える 1 行の文面は、実装したものを見てもらう

## 代案

- **「タスク索引」（`heddleway:task-index`）**: 本質は「タスクを引く索引」なので一度この名前にした。索引の 1 項目を「トピック」にしたので、名前も「トピック索引」に揃えた（タスクは引いた結果の見え方）
- **Murmur の名前を表でも使い、説明を足す**: 名前から中身が想像できない問題は残る。複数の組織の Heddleway につないでいるとき、「どの組織のトピック索引か」のほうが自然
- **索引の 1 項目を「タスク」と呼ぶ**: FYI のメールや雑談までタスクと呼ぶことになる（2026-11-08 に一度この案にして、直樹の指摘でやめた）
- **表でも「スレッド」を使う**: 分かりにくいという背景の 3 が残る
- **内側の言葉も含めて全部改名する**（`thread` → `topic`、`signal` → `message` など）: 一貫するが、API・イベント・投影・テスト・ADR の言い換えが大きい。表の言葉が落ち着いてから考えればよい
