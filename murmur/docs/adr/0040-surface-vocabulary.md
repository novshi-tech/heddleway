# 0040 ユーザーに見せる言葉を整理する。「Murmur」と「名指し」を表に出さない

- 状態: 案（2026-11-08、直樹の指摘から）。採用したら、スキル・ゲートウェイの画面・プラグインの説明・`CLAUDE.md` を直す。過去の ADR は書き換えない
- 関連: 0012（抽出と追跡）、0023（Murmur はゲートウェイの機能）、0038（担当と名指し。この ADR で表の言葉を改める）、0039（言葉の節。タスク・メモ・操作）、H9

## 背景

スキル（`plugins/heddleway/skills/murmur/SKILL.md`）を読んだときに、次の 2 つが分かりにくい（2026-11-08、直樹）。

1. **「Murmur」という名前が唐突**: スキルの説明は「連絡の索引「Murmur」(プロトタイプ)」で始まり、本文にも 35 回出る。ユーザーが使っているのは Heddleway（ゲートウェイ）で、Murmur はその機能の 1 つ（0023）なのに、別の製品のように見える。ユーザーが名前から何をするものかを想像できない。説明も揃っていない（スキルは「連絡の索引」、プラグインの説明は「チームの仕事の記憶」）。ゲートウェイの画面にも「Murmur を有効にしますか?」「Claude や Murmur など」と出る
2. **「名指し」が分かりにくい**: 0038 で決めた言葉で、スキルに 29 回出る。日常の「名指し」は「特に名前を挙げて指す（多くは非難）」の意味で、「宛先に入っていて、確認済みにするまで残るもの」とは結びつきにくい。「名指しを外す」も、何をする操作かが読み取れない。一方で、スキルの例には「自分宛てのものは？」があり、0038 の「リスト宛て」もある。**ユーザーの言葉はすでに「宛て」**になっている

言葉には 2 つの層がある。

- **内側の言葉**: ADR・コード・API の名前（`murmur`・`identity:murmur`・`attention`・`acknowledge`・`ThreadClaimed` など）。設計の議論で使い、変えるとコストが大きい
- **表の言葉**: ユーザーが目にする言葉と、スタンド（Claude）がユーザーに話す言葉。スキルの説明・本文、ゲートウェイの画面、プラグインの説明

今は内側の言葉がそのまま表に出ている。

## 決定（案）

### 1. 「Murmur」は内側の名前に留め、表では「連絡の追跡」と呼ぶ

- 表に出す機能名は「**連絡の追跡**」（Heddleway の機能）。何をするかが名前で分かる。0012 の「抽出と追跡」とも合う
- 内側では Murmur のまま: ディレクトリ `murmur/`、上流のサービス名 `murmur`、`identity:murmur`、ADR、コード。API のパスとトークンの名前は変えない
- スキルの説明の書き出しを揃える: 「Heddleway の連絡の追跡(メール・Teams・Jira・To Do などの連絡をスレッドにまとめ、誰の番かを追う)を…」。プラグインの説明の「Murmur(チームの仕事の記憶)」も同じ言葉にする
- スキルの本文では、上流のサービス名や `identity:murmur` のように**名前が要るところだけ** `murmur` と書く。「Murmur は外に何も書かない」のような説明文は「連絡の追跡は…」か主語を省く
- ゲートウェイの画面: 「Murmur を有効にしますか?」→「連絡の追跡を有効にしますか?」に、何を読むか（読むだけで書かない）の 1 行を添える。接続中のアプリの一覧も「連絡の追跡」と出す
- スキルの名前（`heddleway:murmur`）を変えるかは未決 1

### 2. 「名指し」は表では「宛て」と呼び、外す操作は「確認済みにする」と呼ぶ

| 内側（0038・API） | 表の言葉 |
| --- | --- |
| 名指し（`attention`） | **宛て**（自分宛て・相手宛て。宛先から溜まり、確認済みにするまで残る） |
| 名指し（`attention.named`） | 自分宛て（本人の名前で）／相手宛て（読者でない相手） |
| リスト宛て（`attention.list`） | リスト宛て（今のまま） |
| 名指しを外す（`acknowledge`） | **確認済みにする**（読んで、対応が要るか FYI かを決めた） |
| `myTurn` の理由 `assignee` / `named` / `list` | 担当 / 自分宛て / リスト宛て |

- 「宛て」は宛先そのもの（メールの To・CC）ではなく、**宛先から溜まって、確認済みにするまで残るもの**、と言葉の節で 1 回だけ定義する。言い回しは「自分宛てが残っている」「相手宛てを確認済みにする」
- 「確認済み」は既読ではない。ソースの既読・未読とは連動しない（0038 の決定 3 のとおり、明示的な操作だけ）。スキルにそう 1 行書く
- 「相手待ち」は「相手宛てが残っているもの」で説明できる（言葉は今のまま）
- 選ばなかった言葉:
  - 「メンション」: Teams・Slack の言葉で、メールの To・CC に合わない
  - 「未読」「既読」: ソースの既読と混ざる
  - 「呼びかけ」「要確認」: 「自分宛て」「リスト宛て」とつながらない
- API の名前（`attention`・`acknowledge`・`AttentionAcknowledged`）は変えない（内側の言葉）

### 3. スキルの冒頭に言葉の対応表を置き、スタンドはユーザーに内側の言葉を出さない

- スキルの「言葉」の節に、表の言葉・意味・API の名前の対応表を置く（決定 2 の表と、担当・スレッド・リスト・メモ）
- スタンドは、ユーザーに話すときは表の言葉を使う。API の名前（`my_turn`・`acknowledge` など）は、ユーザーが聞いたときだけ出す
- ほかの内側の言葉（スタンド・読者・名乗る・シグナル・綴じる）をどこまで表の言葉にするかは未決 2

### 4. 直す範囲

- 直す: スキル（`murmur` と、To Do の手順で Murmur に触れる `microsoft-graph` の `references/todo.md`）、プラグインの説明（`plugin.json`・`marketplace.json`）、ゲートウェイの画面（`src/web/`）、`README.md` の表に出る説明、`murmur/CLAUDE.md` の「誰の番」の行（内側と表の言葉の対応を 1 行足す）
- 直さない: 過去の ADR（経緯の記録）、コードの識別子、API。コードのコメントとテスト名の「名指し」は内側の言葉として残してよい（直すなら別の PR）
- スキルを直したらプラグインの版を上げる

## 未決

1. **スキルの名前**: `heddleway:murmur` のままにするか、`heddleway:follow-up` などに変えるか。変えると、スキルの一覧で何をするものかが分かる。代わりに、`murmur` スキルを参照している他のスキル（`microsoft-graph` の To Do など）と、導入済みの環境での呼び名が変わる
2. **ほかの内側の言葉**: スタンド（表では「Claude」）、読者（「見られる人」）、名乗る（「自分のアカウントを結ぶ」）、シグナル（「1 通」「投稿」）、綴じる（「まとめる」）を、この ADR でまとめて表の言葉にするか、気になったときに直すか
3. **「宛て」でよいか**: 「宛て」は宛先と近すぎて、確認済みにするまで残ることが伝わらないかもしれない。使ってみて分かりにくければ見直す

## 代案

- **Murmur の名前を表でも使い、説明を足す**: 名前を残して「Murmur は Heddleway の連絡の追跡の機能」と毎回説明する。名前から中身が想像できない問題は残る。複数の組織の Heddleway につないでいるとき、「どの Murmur か」より「どの組織の連絡の追跡か」のほうが自然
- **内側の言葉も含めて全部改名する**（`attention` → `addressed` など）: 一貫するが、API・イベント・投影・テスト・ADR の言い換えが大きい。表の言葉が落ち着いてから考えればよい
