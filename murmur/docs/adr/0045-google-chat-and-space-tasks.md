# 0045 Google Chat を取り込み、スペースのタスクをスペースの共有リストにする

- 状態: 案（2026-11-17）。S0 の前半（Tasks の側）は `docs/research/2026-11-17-google-chat-space-tasks-s0.md`。後半（Chat の側）はゲートウェイに Chat のサービスを足してから。論点のレビュー待ち
- 関連: 0009（区切りの 4 段）、0012（外には書かない）、0024（購読は本体が持つ）、0030（Contact とアドレス）、0031（決まった形の写し）、0033（リンクは両端を読める人にだけ見える）、0035（アクションの範囲）、0036（Teams のチャネル。この ADR の Chat のスペースの手本）、0037（共有リストはスペース単位。**決定 3 を改める案を含む**）、0038（担当と名指し）、0039（タスクは外のタスクのサービスから写す）、0041（Google は見回り。Google Tasks のコネクタ）、0044（Teams のチャット。この ADR の Chat の DM の手本）、H3・H5・H8

## 背景

Microsoft 365 の組織では、Teams のチャネル（0036）とチャット（0044）が入った。Google Workspace の組織のデプロイには、まだチャットのコネクタがない。Google Workspace の組織では、依頼や確認は Gmail より Google Chat で来ることが多く、Teams の 0044 の背景と同じことが起きる（「自分宛てのものは?」にチャットの依頼が出てこない、結ぶ先がない、`record_sent` が観測と 1 つにならない）。

Google Chat のスペースには、**スペースのタスク**がある。スペースのメンバーが作り、メンバーに割り当て、スペースの「タスク」タブで全員が見る、スペース単位の共有のタスクリストである。チームの「誰が何を持っているか」がここにあり、0037 の共有リストの形（スペース単位、読者はメンバー）にそのまま重なる。

ただし、S0 の前半で次のことが分かった。

- スペースのタスクを、スペースのタスクとして一覧する API は見当たらない。Tasks API の `tasklists` にも出ない
- 見えるのは、**割り当てられた人の既定のリストの写し**だけ。`tasks.list` に `showAssigned=true` を付けたときだけ、`assignmentInfo.spaceInfo.space`（`spaces/<ID>`）付きで出る
- したがって 1 人の委任では、そのスペースの「自分に割り当てられたタスク」しか読めない。割り当てのないタスクと、つないでいない人のタスクは読めない
- 今の Google Tasks のコネクタ（0041）は `showAssigned` を付けていないので、スペースのタスクはどの個人リストにも入っていない
- 一方、UI ではスペースのメンバー全員が、割り当てのないものも含めてスペースのタスクを見られる。Google のヘルプによると、タスクの作成・更新のたびにスペースに通知のメッセージが出て、タスクが消えてもメッセージは残る。このメッセージが Chat API で読めれば、スペースのタスク全体をつないだ人 1 人の委任で追える（S0 の後半でまず確かめる）

0037 の決定 3 は「共有リストは、つないだ人 1 人の委任で読む」。スペースのタスクはこの形では読めない。

## 決定（案）

### 1. Google Chat のスペースは共有リスト（0036 の形）

- `spaceType` が `SPACE` のスペース 1 つが、1 つのスペース・1 つの共有リスト（0037 の決定 1）。名前は「<スペースの名前>」
- 読者はスペースのメンバー（`spaces.members.list`）のうち Murmur の User。ゲートウェイのサインインが Google なら、ゲートウェイの User ID（`google_<sub>`）の sub と、Chat のメンバーの `users/<ID>` の ID は同じ Google のアカウントの ID なので、名乗りなしで対応が付く（0037 の決定 2 の「同じ IdP」。同じであることは S0 の後半で確かめる）
- 経路はつないだ人の委任（ゲートウェイの新しいサービス `chat`）。作れるのはメンバーなら誰でも、デプロイの設定 `MURMUR_SHARED_SERVICES` に `google-chat` があるとき（0037 の決定 4）
- 区切り: Chat のスレッド（`thread.name`）をアンカー `threadTs` にする（0036 の決定 3 と同じ。スレッドの返信は構造で入り、新しいスレッドの最初のメッセージは AI の区切りに回す）。スレッドなしのスペース（インラインの返信を使わない古い形）は、メッセージごとに AI の区切り
- 名指し: 個人へのメンション（`annotations` の `USER_MENTION`）を宛先にする。`@all` は個人に落とさない。メンションのないものは宛先なしで、担当する操作（`ThreadClaimed`）を待つ（0036 の決定 4、0038）
- 編集・削除・リアクション・アプリ（ボット）の投稿は取り込まない

### 2. DM とグループのチャットは、本人の個人リスト 1 つ（0044 の形）

- `spaceType` が `DIRECT_MESSAGE` と `GROUP_CHAT` のスペースを、まとめて「Google Chat のチャット」という個人リスト 1 つにする（1 人に 1 つ）
- 区切りの候補は会話（`Anchors.conversationId` にスペースの名前、`conversationGroup` は `GROUP_CHAT` なら真）で同じスペースに限る。0044 で足した仕組みをそのまま使う
- 名指しは 0044 の決定 3 と同じ: DM は相手のメッセージ全部、グループはメンションだけ
- 相手がアプリだけの DM は取り込まない（0044 と同じ）

### 3. アドレス: チャネル `google-chat`、値はアカウントの ID

- `Channel` に `google-chat` を足し、値は `users/<ID>` の ID（数値の文字列）。DM とスペースで同じ人は同じアドレス
- つないだとき・読者を写すときに、本人の Contact に本人の `google-chat` のアドレスを付ける（sub から分かる）
- Chat のメッセージの `sender` には、委任で読んでも表示名やメールアドレスが入らないことがある（S0 の後半で確かめる）。相手の Contact は 0035 のとおりエージェントが作る

### 4. 取り込み: 見回り（0041 の決定 1）

- Pub/Sub と Workspace Events API は使わない（0041 と同じ理由。デプロイの設定が重い）。5 分ごとの `maintain` で読む
- スペース: `spaces.messages.list` を `filter=createTime > "<前回 − 重なり>"` で読む（Chat の一覧の絞り込みは `createTime` だけ）。二重は `sourceRef`（`google-chat:<message name>`）で落ちる
- 個人リスト: `spaces.list` で本人のスペースを読み、`lastActiveTime` が前回より新しい DM・グループだけを、同じく `messages.list` で読む。1 回の見回りで読むスペースの数に上限を置く（0044 と同じ）
- 量の見積もりと Chat API のクォータ（1 ユーザーあたりの読み取りの上限）は、S0 の後半と試用で見る

### 5. スペースのタスクは、そのスペースの共有リストに状態を持つソースとして写す

チャットとタスクを別のリストにはしない。**1 つのスペースの共有リストに、メッセージのスレッドと、タスクの写しのスレッドの両方が入る**（Jira の課題のスレッドと同じく、タスク 1 つが 1 つのスレッド）。

- 写しは 0031 の決まった形: `closed` は完了（削除も閉じる）、`holders` は割り当てられた人（写しを読んだリストの持ち主）、`title`、`statusLabel` は「スペースのタスク」、`due` は期限の日付
- 担当の出所は、状態を持つソースなので `holders`（0038 の決定 1）。スペースの中で割り当てを替えると、写しの `holders` が替わる
- 区切りの鍵は、タスクの写しの ID（`gtasks-space:<spaces/ID>/<task id>`）。割り当てを替えたときに ID が変わるなら、スレッドが 2 本になる（S0 の後半。変わるなら未決 2）
- タスクのスレッドとメッセージのスレッドは自動で結ばない（0014）。結ぶのは人とエージェント

### 6. スペースのタスクの読み方: スペースのメッセージを先に試し、だめなら読者それぞれの委任

- **経路 A（第一の候補）**: スペースのタスクの通知のメッセージが Chat API で読め、タスクを識別できて状態（作成・担当・完了・削除）が分かるなら、スペースのメッセージの見回りの中でタスクの写しを作る。つないだ人 1 人の委任で足り、0037 の決定 3 は改めない。割り当てのないタスクも入る
- **経路 B（A が使えないとき）**: 下のとおり、読者それぞれの Google Tasks の委任を合わせて読む
- A で写せるのが一部（例えばタイトルと作成だけで、完了が分からない）なら、A で作って B で状態を補う組み合わせも考える

以下は経路 B。

- スペースの共有リストの読者のうち、ゲートウェイで Google Tasks をつなぎ、トピック索引を有効にしている人について、**その人の委任で**既定のリストを `showAssigned=true` で読み、`assignmentInfo.spaceInfo.space` がこのスペースのものだけを写す
- 0037 の決定 3 を「共有リストは、つないだ人 1 人の委任で読む。**ただし、ソースが各メンバーに割り当てた分しか見せないもの（スペースのタスク）は、読者それぞれの委任で、その人に割り当てられた分を読む**」に改める
- 情報が広がらないこと: 読む人はスペースのメンバー（読者）で、写す先もそのスペースの読者だけ。スペースのタスクはスペースのメンバー全員が UI で見られるものなので、読者に見せても範囲は広がらない
- **取りこぼし**: 割り当てのないタスクと、Google Tasks をつないでいない人のタスクは入らない。スキルでそう案内する（「スペースのタスクは、割り当てられた人が Google Tasks をつないでいるものだけ見えます」）。S0 の後半で、スペースにタスクの作成のメッセージが残り Chat API で読めると分かれば、作った人の委任で割り当てのないタスクも拾う道を足す（未決 1）
- 読む経路は Google Tasks のコネクタの見回りに乗せる。読者の Google Tasks の接続 1 つにつき、既定のリストを 1 回読み、`spaceInfo.space` でスペースの共有リストに振り分ける（スペースの数だけ読み直さない）

### 7. 本人の Google Tasks の個人リストには、スペースのタスクを入れない

- 今のまま `showAssigned` を付けない。スペースのタスクの居場所はスペースの共有リスト 1 つにして、同じタスクが個人リストと共有リストの 2 本のスレッドにならないようにする
- スペースの共有リストがない（誰もそのスペースをつないでいない）スペースのタスクは、どこにも入らない（未決 3）

### 8. ゲートウェイ

- カタログに Google Chat のサービス `chat` を足す（`chat.googleapis.com`。スコープは読み取りの `chat.spaces.readonly`・`chat.messages.readonly`・`chat.memberships.readonly` と、エージェントが投稿するための `chat.messages.create`）。デプロイの手順に「Google Cloud のプロジェクトで Chat API を有効にし、Chat アプリの構成（名前とアイコン）を作る」を足す（Chat API はユーザーの認証でも Chat アプリの構成を要求する）
- 読める口を 2 つ足す: `google-chat`（スペースの共有リスト。`spaces/{space}` の GET・`members` の GET・`messages` の GET。つなぐときの `spaces` の一覧）と `google-chat-dm`（個人リスト。`spaces` の一覧・`messages` の GET・`members` の GET）。投稿の口は通らない。共有リストの経路から、窓口の人の DM を読めないようにする（0044 の決定 6 と同じ）
- Google Tasks の読める口（`gtasks`）は今のまま（クエリの `showAssigned` を通すだけ）

### 9. つなぎ方と API

- `POST /connections/google-chat`（`space` を省けば、つなぐ人が読めるスペースの一覧で `choose_space`）。スペースの共有リスト
- `POST /connections/google-chat-dm`（選ぶものはない）。本人の個人リスト
- スペースのタスクのためにつなぐものはない。スペースの共有リストの読者が Google Tasks をつないでいれば、自動で入る
- スキル: topic-index に「Google Chat のスペースをつなぐ」「Google Chat のチャットをつなぐ」と、スペースのタスクの見え方（決定 6 の取りこぼし）。プラグイン `heddleway-google` に Google Chat のスキル（スペースの一覧・メッセージの読み書き・`record_sent` の `sent_ref` はメッセージの `name`）

## 論点（レビューで決めたい）

1. **スペースのタスクを、チャットと同じ共有リストに入れるか、スペースごとに別の共有リスト（「<スペース>のタスク」）にするか**: 案は同じリスト。1 スペース 1 共有リスト（0037 の決定 1）を崩さず、読者の写しも 1 回で済む。別にすると、チャットは取り込まずタスクだけ共有したいスペースに向く
2. **読者それぞれの委任で読むこと（決定 6）を受け入れるか**: 0037 の決定 3 を改める。代わりに「スペースのタスクは、割り当てられた人の Google Tasks の個人リストに入れる（`showAssigned` を付けるだけ）」なら 0037 は改めずに済むが、共有リストにはならない（ほかのメンバーから「○○さんが持っている」が見えない）
3. **経路 B のときの取りこぼし（割り当てなし・つないでいない人の分）を受け入れるか**: 案は受け入れてスキルで案内する。経路 A が使えれば起きない
4. **Google Chat の DM・グループ（決定 2）を同時に入れるか**: 案は同じ ADR で決め、実装はスペース → タスク → DM の順に分ける

## 代案

- **A. スペースのタスクを、割り当てられた人の個人リストに入れる**（論点 2）: 0037 を改めない。ただ、頼まれた「共有リストとして使う」にならない
- **B. スペースのタスクをアプリの権限（ドメイン全体の委任）で読む**: 管理者がサービスアカウントにドメイン全体の委任を付ければ、メンバー全員になりすまして読める。全員のタスクが読めるが、テナントの全員のタスクとチャットに届く権限を本体に持たせる。0036 の代案 A・0042・0044 の代案 C と同じ理由で使わない
- **C. Workspace Events API と Pub/Sub で通知を受ける**: 遅れが減るが、0041 の決定 1 と同じくデプロイの設定が重い。見回りで足りなければ後から足す

## 帰結

- 0037 の状態に「決定 3 を 0045 で改めた（スペースのタスク）」を注記する
- ドメイン: `Channel` に `google-chat`。スペースの共有リストのデータソースが、メッセージ（シグナル）と状態の写しの両方を受ける（Jira と同じ）。写しの `holders` の出所が読者の委任ごとに違うこと（読者 A の委任が A を `holders` にする）。読者が外れたら、その人の委任で読んだタスクの写しをどうするか（未決 4）
- コネクタ: `src/connectors/google-chat/`（スペースと DM。正規化・見回りの計画は純関数）、`gtasks/` に「既定のリストの割り当てられたタスクを読み、スペースの共有リストに振り分ける」を足す
- ゲートウェイ: カタログの `chat`、読める口 2 つ、デプロイの手順（Chat API と Chat アプリの構成）
- API とスキル: 決定 9
