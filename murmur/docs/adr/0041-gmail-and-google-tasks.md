# 0041 Gmail と Google Tasks のコネクタ。Google の取り込みは見回りから始める

- 状態: 採用（2026-11-11、直樹とのディスカッション。見回りで始めることと、見回りの量の見積もりを確かめて採用した）。同じ日に実装した（下の「実装で決めたこと」。スキルは heddleway 0.25.0・heddleway-google 0.15.0）。Google Workspace の組織のデプロイでの確かめは、まだ
- 関連: 0024（外部コネクタ。Webhook は本体が持つ）、0039（タスクは外のタスクのサービスから写す。決定 3 の表に Google Tasks の写しがある。未決 3 で「To Do の次」とした）、0031（決まった形の写し）、0038（担当と名指し）、0023（ゲートウェイの機能。読める口はゲートウェイの入口が固定する）、0025（共有のアドレス）、0040（表の言葉）、ゲートウェイの `docs/adr/0004`（1 つのデプロイ = 1 つの組織）

## 背景

個人リストのコネクタは、Microsoft 365 の組織のもの（Outlook と To Do）しかない。Google Workspace の組織のデプロイでは、個人リストを 1 つも作れず、メモ（個人リストのスレッドにしか書けない。0039）も使えない。

足すのは 2 つ。

- **Gmail**: 本人のメールボックス。Outlook と同じ、読者が本人 1 人の個人リスト
- **Google Tasks**: 本人のタスクのリスト。To Do と同じ、個人リストの状態を持つソース（0039 の決定 3）

データモデルは変えない。どちらも、今あるチャネル（`email`・`todo`）と写しの形に載る。決めることは、Google の側の取り込みの経路だけ。

Microsoft Graph と違うところ:

- **Gmail の変更の通知は、Cloud Pub/Sub を通る。** `users.watch` は通知の宛先に Pub/Sub のトピックを取り、HTTPS の URL を直接は取らない。受けるには、デプロイごとに Google Cloud のプロジェクトにトピックとプッシュのサブスクリプションを作り、Gmail に発行の権限を付ける。watch は 7 日で切れる
- **Google Tasks には、変更の通知がない。** 差分は `updatedMin` で取る（0039 の決定 3 でもう決めた）
- **Google は API ごとにサービスが分かれている。** ゲートウェイの接続も `gmail` と Tasks で別になる。Graph のように、スコープを足すと既存の接続が全部つなぎ直しになることはない

## 決定（案）

### 1. Google の取り込みは、見回りで行う

Gmail も Google Tasks も、5 分ごとの見回り（今の `maintain`）で差分を取る。Pub/Sub は使わない。

- Tasks は通知がないので、Google の側には見回りの仕組みがどのみち要る。Gmail も同じ仕組みに載せれば、経路が 1 つで済む
- Pub/Sub は、デプロイする人に Google Cloud の設定（トピック、サブスクリプション、権限）を足す。セルフホストの手順が重くなる
- 遅れは最大 5 分。トピック索引は、エージェントが見に来たときに「誰の番か」を答えるもので、届いた瞬間に人を呼ぶものではない。Outlook でも、通知を取りこぼしたときの保険は同じ見回りの delta
- Outlook より遅くなることは受け入れる。足りなければ、Pub/Sub をデプロイの任意の設定として後から足す（未決 1）。足しても、見回りは保険として残る

0024 の決定 1（購読の管理は本体が持つ）は変えない。Google には、いまは購読がないだけ。

見回りを足すのに合わせて、次の 2 つを入れる。

- **見回り 1 回につき、マスタの読み込みを 1 回にする。** 今は、コネクタごとに全データソースを回り、データソース 1 つごとにマスタを読み直している。データソースの数の掛け算で増えるので、見回りの始めに 1 回読んで使い回す
- **Google Tasks の見回りの間隔を、Gmail と別に決められるようにする。** 既定はどちらも 5 分（Cron の間隔）。Tasks の 1 日の上限に近づいたら、デプロイの設定で Tasks だけ間隔を延ばす

### 2. Gmail: 本人のメールボックスを個人リストにする

- チャネルは `email`、経路は `gmail`。データソースの作り方・読者・アイデンティティは Outlook と同じ（`domain/connection.ts`）。本人のアドレスと、送信元として使える別名（`settings/sendAs`）が、本人の Contact に付く
- **差分は履歴で取る。** つないだときの `historyId` を覚え、見回りで `users.history.list`（`messageAdded`）を読み、増えたメッセージを `messages.get` で取る。取り込むのはつないだあとのメールだけ（Outlook と同じ）
- **履歴が切れていたら**（`startHistoryId` が古すぎると 404）、最後に読めた時刻より後のメッセージを検索（`messages.list` の `after:`）で拾い直し、いまの `historyId` から続ける。同じメッセージが 2 度来ても、`sourceRef` の重複排除で 1 つになる
- **取り込むメッセージ**: 受信と送信の両方（Outlook と同じ。送信を取るので、記録した送信と Message-ID で 1 つになる。H5）。下書き・迷惑メール・ゴミ箱・チャットのラベルが付いたものは取らない
- **正規化は Outlook と同じ形**（純関数）: `sourceRef` は `email:<Message-ID>`、アンカーは `messageId` と `inReplyTo`、宛先は To と Cc。本文は `text/plain` の部分を使い（なければ HTML からテキストにする）、引用の履歴を落とす（Outlook の `stripQuoted` を共有する）
- Gmail のスレッド（`threadId`）は区切りに使わない。区切りは今までどおり、アンカーと Ingest の判断で決める。件名が同じだけで別の用件が 1 つの Gmail のスレッドになることがあるため
- スター・ラベル・既読は写さない（名指しは既読と連動しない。0038）

### 3. Google Tasks: 本人のタスクのリストを個人リストにする

0039 の決定 3 のとおり。足りなかったところだけ決める。

- チャネルは `todo`、経路は `google-tasks`。タスクのリスト 1 つにデータソース 1 つ。本人がつなぐときに選び、いくつでもつなげる（To Do と同じ）
- **差分は `updatedMin` で取る。** 見回りで、リストごとに「前回より後に変わったタスク」を読む。完了・非表示・削除も読む（`showCompleted`・`showHidden`・`showDeleted`）
- 写しは 0039 の表のとおり: `closed` は完了（削除・非表示も閉じる）、`holders` は本人、`title`、`statusLabel` はリストの名前、`due` は期限の日付（Google Tasks の `due` は日付だけが意味を持つので、日付の部分をそのまま使う）。`notes` は写さない
- **サブタスクは、親と同じ 1 つずつのタスクとして写す。** 親子は写さない（リンクは人とスタンドが張る。0014）
- つなぐ前に完了したきりのタスクは取り込まない（To Do と同じ）
- Gmail から作ったタスクに付くメールへのリンクは、アンカーとして取り込めるかを実物で確かめてから決める（未決 3）

### 4. ゲートウェイの側

- **カタログに Google Tasks のサービスを足す**（スコープは `https://www.googleapis.com/auth/tasks`。スタンドがタスクを作る・完了にするので読み書き）。Gmail は今のサービス（`gmail.modify`）のまま
- **取り込みに使うサービスの種類を 2 つ足す**（`gmail` と Google Tasks）。読める口は入口が固定する（0023）
  - Gmail: `users/me` の下の読み取り（プロフィール・履歴・メッセージ・ラベル・`settings/sendAs`）だけ。送信・下書き・ラベルの変更・削除の口はない
  - Google Tasks: `users/@me/lists` と `lists/*/tasks` の読み取りだけ
- 同意は今のもの（本人がゲートウェイの画面でトピック索引を有効にする）。Google のためには足さない
- どのコネクタが使えるかは、デプロイにそのサービスがあるかで決まる。Google Workspace の組織のデプロイでは Gmail と Google Tasks、Microsoft 365 の組織のデプロイでは Outlook と To Do をつなぐ（0039 の決定 4）。本体は IdP の種類を見ない

### 5. API とスキル

- API: `POST /connections/gmail`（Outlook と同じ流れ）、`POST /connections/google-tasks`（To Do と同じ流れ。`choose_list` でリストを選ぶ）。`GET /connections` の `kind` に `gmail` と `google-tasks` を足す
- スキル（`heddleway:topic-index`）: 「Gmail をつなぐ」「Google Tasks をつなぐ」を足す。「To Do のタスクで追う」は、タスクのサービスがどちらでも同じ流れになるように書き直す（作る・完了にするのは、その組織のタスクのサービスのスキルで）
- スタンドが Google Tasks に書くためのスキルを、プラグイン `heddleway-google` に足す（0039 の帰結に書いてあったもの）
- Gmail で送ったあとの `record_sent` の `sent_ref` は Message-ID（今の決まりのまま）。Gmail の送信の API が返すのはメッセージの ID なので、送ったメッセージのヘッダーから Message-ID を取る手順を gmail のスキルに書く

### 6. 進める順番

1. ゲートウェイ: Google Tasks のサービス、サービスの種類と読める口
2. Google Tasks のコネクタ（小さい。To Do の形をなぞり、見回りの差分を作る）
3. Gmail のコネクタ
4. スキルとプラグイン（Google Tasks のスキル、topic-index の書き直し）
5. Google Workspace の組織のデプロイで、トピック索引を有効にして確かめる

## 実装で決めたこと（2026-11-11）

実装とレビューで、上の決定に足したこと・改めたこと。

### 読める口の照合を、送るパスで行う（全コネクタ）

読める口（0023）は、生のパスの文字列で照合し、実際に送るのは正規化したあとのパスだった。`..` や `\` を混ぜると、許された口の形のまま別のパスに届いた（メソッドとホストは守られていた）。Google の口を足す前からあった穴で、Graph・Jira・Teams の口も同じだった。

- 照合するパスと送るパスを同じものにした。`\`、`#`、`.` と `..` の区切り、`%2e`・`%2f`・`%5c` を含むパスと、正規化で変わるパスは断る
- メソッドを上書きするヘッダー（`X-HTTP-Method-Override` など）は、口の実装が落とす

### 決定 2（Gmail）に足したこと・改めたこと

- **本人の Contact に付けるのは、メールボックス自身のアドレスだけ。** 「別のアドレスから送信」（`settings/sendAs`）のアドレスは付けない（決定 2 の「別名が本人の Contact に付く」を改めた）。グループのアドレスのように、複数の人が同じアドレスを持てるので、1 人のものにすると次の人がつなげない。別名は、人とスタンドがあとから付ける（0030）
- **取り込むのは、受信トレイか送信済みのラベルが付いたメッセージだけ。** フィルタで受信トレイを飛ばしたメールやアーカイブ済みのメールは取らない（Outlook が受信トレイと送信済みだけを読むのに合わせた）
- **1 回の見回りで取り込むのは、メールボックス 1 つにつき 50 通まで。** 10 通ごとに履歴の位置を保存する。同じメッセージで 3 回続けて失敗したら、記録して飛ばす（1 通でメールボックスが止まらないように）
- **履歴が切れたときの拾い直しは、先に ID を集めてから、古い順に取り込む**（上限 2,000 通。スレッドの中の順番は取り込んだ順なので）
- **本文には上限がある**（読むのは 1 つの部分につき 256KB まで、残すのは 10 万文字まで）。HTML をテキストにする処理は、長さに比例する時間で終わるようにした（外から届く 1 通で見回りが止まらないように）
- 引用の履歴を落とす処理は、引用の間に返事を書く形のメールでは、引用の行だけを落として返事を残す

### 決定 3（Google Tasks）に足したこと

- **差分の位置は、読み始めた時刻より先に進めない。** Google Tasks はタスクを更新の順ではなく並びの順で返すので、読んでいる間に変わったタスクを取りこぼさないため。同じタスクをもう一度読むことはあるが、写しは変わった項目しか書かない
- 1 回の見回りで読むのは 20 ページまで。残りは次の見回りで、同じ問い合わせの続きから読む
- リストの名前の変更は、1 時間に 1 回確かめる。変わっていたら、リストを読み直して写しの `statusLabel` を直す
- 件名のないタスクは、開いていれば取り込まない。閉じた（完了・削除・非表示）ものは、すでにあるスレッドを閉じるだけ

### 決定 4（ゲートウェイの側）を改めたところ

- **Google Tasks のサービスの向き先は `https://www.googleapis.com`、スコープは `auth/tasks` と `auth/userinfo.email`。** Tasks の API には「つないだアカウントが誰か」を返す口がない。同じホストの `oauth2/v3/userinfo` で本人のアドレスを読み、チャネル `todo` の本人のアドレスにする（To Do が Graph の `/me` で読むのと同じ役目）。確認済みでないアドレスならつながない
- Google Tasks の読める口に、`oauth2/v3/userinfo` の読み取りを足した
- 見回りの間隔は、デプロイの設定 `MURMUR_TASKS_POLL_MINUTES`（Google Tasks だけ。なければ毎回）

### Google のエラーの読み方

- 上限のエラー（429、403 の `rateLimitExceeded`・`dailyLimitExceeded` など）は、次の見回りでやり直す。データソースは壊れた扱いにしない
- API が有効になっていないエラー（403 の `accessNotConfigured`・`SERVICE_DISABLED`）は、本人の同意の問題ではなく、デプロイの設定の問題として `broken` にする（理由に、ゲートウェイの Google Cloud のプロジェクトで API を有効にすることを書く）

### 同期と接続の共通の直し

- 読み取りの途中で本人が外した・つなぎ直したときに、同期が古い状態を書き戻さない（Gmail と Google Tasks。書く前に読み直し、同期が持つ項目だけを直す）。**Outlook・To Do・Jira・Teams にも同じ問題が元からあり、まだ直していない**
- ゲートウェイで接続を作り直して接続の ID が変わっても、同じメールボックスをつなぎ直せる（Gmail と Outlook）。つなぎ直しでは、外していない限り読み取りの位置を引き継ぐ

## やらないこと

- **共有のアドレス**（Google グループ、共同トレイ）。0025 にあたる形を、Google では別に決める。まず個人リストだけ
- **Google Chat のスペース**の共有リスト
- **Pub/Sub の通知**（未決 1）
- 個人の Google アカウント（組織の外）の Gmail と Tasks（0039 の決定 4 のまま）

## 条件・リスク

- **Gmail の本文の取り出し**は Graph より手間がかかる（MIME の部分をたどる、base64url、HTML だけのメール）。Graph の `uniqueBody` にあたるものがないので、引用を落とすのは自前の `stripQuoted` だけになり、区切りと件名の判断（AI）に渡る本文が Outlook より長くなることがある
- **見回りの量**（2026-11-11 の見積もり。想定は数人から数十人のチーム）: 5 分ごとに、Gmail は 1 人 1 回、Tasks はリスト 1 つに 1 回、上流を呼ぶ。変更がなければ応答はほぼ空
  - Cloudflare の側は余裕がある。キューの消費側は 1 回の実行が 15 分まで、外への呼び出しは 1 回の実行で 10,000 まで（有料プランの既定）、応答待ちは CPU 時間に数えない。見回りは 1 通のメッセージで全データソースを順に回るので（同時実行は 1。0024 の決定 2）、1 つ 0.3 秒として、5 分に収まるのは 1,000 データソースくらいまで
  - **先に当たるのは Google Tasks の API の 1 日の上限**（既定はプロジェクトごとに 5 万回）。5 分ごとだとリスト 1 つで 1 日 288 回なので、170 リストくらいで届く。15 分ごとにすれば 500 リストくらいまで延びる
  - 30 人（90 データソースくらい）なら、何も変えなくてよい。数百人では、データソースごとにメッセージを分けて並列にする作り替えが要る（想定の外）
- **Gmail のスコープは制限付き**（restricted）。組織の内部のアプリなら審査は要らないが、ゲートウェイの Google の OAuth のクライアントを「内部」にしていることが前提（ゲートウェイの 0004）
- 履歴が切れたときの拾い直しは、検索の粒度（秒）と時計のずれで取りこぼしうる。重なりを持たせて検索する

## 実物で確かめること

テストは作り物の API で回している。Google Workspace の組織のデプロイで、次を確かめる。

- Gmail: 下書きを送ったとき（画面と API）に、送信済みのラベルが付いた新しいメッセージとして履歴に出るか
- Gmail: 迷惑メールから戻したメールが取り込まれるか（履歴は「メッセージが増えた」しか読んでいない）
- Gmail: 履歴に出るラベルは、増えた時点のものか、いまのものか
- Gmail: 一覧の続きの印（`pageToken`）が、見回りをまたいで使えるか
- Gmail: POP などで取り込んだ、受信の時刻が古いメールが、拾い直しの範囲から外れないか
- Gmail: 大きい本文が、中身なしで添付の ID だけで返ることがあるか（添付の口は読める口にない）
- Google Tasks: `updatedMin` がその時刻を含むか。削除・非表示が `updated` を進め、差分に出るか
- Google Tasks: Google の画面で完了にしたタスクが、非表示（`hidden`）として返るか
- Google Tasks: `userinfo` が、Workspace のアカウントで確認済みのアドレスを返すか
