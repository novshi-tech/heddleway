# 0043 表の言葉から「番」をなくし、「担当」と「アテンション」で言う。タスクは担当のものと、アテンションのうち読んでタスクと分かったもの

- 状態: 採用（2026-11-17、直樹とのディスカッション）。0040 の決定 2 の「タスク」の意味と、決定 4 の「そのまま使う言葉」の「自分の番」を改める。過去の ADR は書き換えない
- 関連: 0008（業務の知識を持たない）、0038（担当と名指し。この ADR は表の言葉だけを改め、モデルは変えない）、0039（To Do のタスクで追う）、0040（表の言葉。この ADR で改める）

## 背景

0040 は、表の言葉で「タスク = 自分の番のトピック（担当が自分か、自分へのアテンションが残っているもの）」とし、「誰の番か」「自分の番」をそのまま使った。スキル・`README.md`・プラグインの説明・同意の文面・管理画面に「誰の番かを追う」が出ている。

「番」に違和感がある（2026-11-17、直樹）。代わりに「ターン」「ボール」を考えたが、どれも当てはまらないことが分かった。

- 日常の「番」「ターン」「ボール」は、**1 つしかなく、やりとりのたびに交互に移るもの**を指す。これは 0038 でやめたモデル（スレッドごとに 1 つの値 `us / user / contact / none`、最後に求めたシグナルで上書きして移す、AI の「求めているか」で補う、2 者の会話を前提にした 2 段）そのもの
- 0038 の今のモデルでは、担当とアテンションは独立した 2 つの軸で、どちらも人を指す。アテンションは宛先から**溜まり**、明示的に外すまで残る。同時に何人にも付く。交互に回ってくるものではない
- 担当もアテンションも「自分のところに来ている」という点では同じで、「番」はその 2 つを 1 つの順番のように見せてしまう
- 0040 の「タスク」は、FYI のアテンションまでタスクに数えていた。FYI はタスクではない

## 決定

### 1. 表の言葉から「番」をなくす。「担当」と「アテンション」をそのまま言う

- 「誰の番か」「自分の番」「その人の番になる」「誰の番でもない」は使わない。何が残っているかを、担当とアテンションの 2 つでそのまま言う
- 「ターン」「ボール」も使わない（背景のとおり、交互に移る 1 つのものを思わせる）

| 今の言い方 | 書き換え |
| --- | --- |
| 誰の番かを追う | 担当とアテンションを追う |
| 自分の番のトピック（`my_turn`） | 自分の担当か、自分へのアテンションが残っているトピック。短く言うときは「自分の担当とアテンション」 |
| その人の番になる（Jira の担当者・Teams のメンション） | その人が担当になる／その人にアテンションが付く |
| 誰の番でもない（完了など） | 担当もアテンションも残っていない |
| 結んだ先から見た番（`derivedBall`） | 結んだ先の様子（`my_turn`: 結んだ先に自分の担当かアテンションが残っている、`waiting`: 結んだ先が全部返事待ち） |
| `myTurn` の理由 | 自分に残っている理由（担当 / アテンション / リスト宛て） |

### 2. アテンションには、タスクと FYI が区別されずに入っている

- アテンションは宛先から機械的に付く「少なくとも見てほしい」の印（0038・0040 のまま）。その中には、潜在的にタスクのものと FYI のものが**区別されずに**入っている。区別するのは、読んだ本人かエージェント。トピック索引は判断しない（0008、0038 の「考え方」）
- 読んだあとの流れ:
  - FYI だった → アテンションを外す
  - タスクだった → 担当する（共有リストは `claim`、状態を持つソースはソースで担当者を移す）か、To Do / Google Tasks のタスクに作って結ぶ（0039）。返事をすれば済むものは、返事を送って `record_sent` の `acknowledge: true` で外す
- アテンションはタスクの受け口で、タスクそのものではない

### 3. 「タスク」は、担当のトピックと、アテンションのうち読んでタスクと分かったもの

0040 の決定 2 の「タスク（自分のタスク）= 自分の番のトピック」を改める。

| 表の言葉 | 意味 | 内側 |
| --- | --- | --- |
| **タスク**（自分のタスク） | 自分が担当のトピック、自分の To Do / Google Tasks のタスク、それと、アテンションのうち読んでタスクと分かったもの | なし（見え方の名前で、API の値ではない） |
| 自分の担当とアテンション | 自分の担当か、自分へのアテンションが残っているトピック。タスクの候補を引く一覧 | `filter=my_turn`・`myTurn` |

- どれがタスクかはトピック索引の中では決まらない（決定 2）。そこで「タスク」は API の値の名前にしない。`filter=my_turn` は「自分の担当とアテンション」を返すもので、それを「タスク」とは呼ばない
- 「今日やることは?」には、エージェントが `filter=my_turn` と `filter=mine`（自分の To Do / Google Tasks のタスク）を引き、アテンションだけのものは本文を読んで、タスクか FYI かを分けて答える。ユーザーが「自分のタスクを見せて」と言うのは自然なので、依頼の言葉としてはそのまま受ける
- 0040 の「索引の 1 項目を『タスク』と呼ぶとタスクでないものまでタスクと呼ぶことになる」という理由は、FYI のアテンションにも当てはまる。この ADR はそれを最後まで通したもの

### 4. 個人リストでは「担当」と言わない

- 0038 の決定 1 では、個人リスト（本人の Outlook / Gmail・本人の To Do / Google Tasks）の担当は本人（暗黙）で、`assignee` は `null` を返し、自分に残っているかはアテンションだけで決まる（`turn.ts`）
- 表では、個人リストに「担当」の軸があるとは言わない。全部が本人のものなので、担当と言うとタスクの意味がぼやける。個人リストで残るのはアテンションで、進めると決めたものは To Do / Google Tasks のタスクで追う（0039）か、メールのトピックにメモを書く
- モデル（0038 の決定 1 の表）は変えない。表の言い方だけを決める

### 5. 直す範囲

- 直す: スキル（`plugins/heddleway/skills/topic-index/SKILL.md`。冒頭の説明、「言葉」の表、「番」の出てくる文、「よくある流れ」の 1 と 6）、プラグインの説明（`plugin.json`・`marketplace.json`）、`README.md`、`murmur/README.md`、同意の文面（`src/murmur-feature.ts`）、管理画面の列見出し（`murmur/src/http/admin.ts` の「誰の番」）、`murmur/CLAUDE.md`（0040 の行を改め、この ADR を足す）
- 直さない: 過去の ADR、コードの識別子と API（`my_turn`・`myTurn`・`derivedBall`・`Turn`）、イベントの名前。コードのコメントとテスト名の「誰の番」は内側の言葉として残してよい（0038 のモデルを指す言葉として通じる。直すなら別の PR）
- スキルの本文が変わるので、`heddleway` プラグインの版を上げる（パッチ。スキルの名前と API は変わらない）

## 代案

- **「ターン」**: API の `my_turn` とそのまま対応する。交互に回ってくる 1 つのものを思わせ、担当とアテンションが同時に何人にも付くモデルと合わない。エージェントの文脈では「会話のターン」ともぶつかる
- **「ボール」**: 仕事の日本語では自然。0038 でやめた、1 つの値を上書きして移すモデルそのものを指してしまう
- **「〜待ち」（自分待ち・誰待ち）**: 「返事待ち」「割当待ち」と揃うが、「自分待ちのトピック」が不自然で、担当の分が入らない
- **「残っている」（自分に残っている・誰に残っているか）**: モデルには素直だが、担当とアテンションを 1 語に束ねる理由がない。束ねずに 2 つの言葉で言えば足りる（決定 1）
- **「タスク」を 0040 の広い定義のままにし、「誰の番か」を「誰のタスクか」に言い換える**: 言葉は楽だが、FYI のアテンションをタスクと呼ぶことになる

## 実装の記録（2026-11-17）

- 決定 5 の「直す」のとおりに直した（heddleway 0.27.2）
