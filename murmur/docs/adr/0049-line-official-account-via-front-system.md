# 0049 LINE 公式アカウントは、受け口（業務システム）の原本を見回りで読み、共有リストにする

- 状態: 採用（2026-11-23、直樹。0019 の受け口を業務システムに置く設計案を見てから）。実装は受け口の側（原本・差分読み・送信）→ この本体のコネクタ（`src/connectors/line/`）→ スキルの順
- 関連: 0012（外には書かない）、0019（LINE のチャネルは手前の別システムが持つ）、0030（Contact とアドレス）、0037（共有リストはスペース単位）、0038（担当と名指し）、0041（見回り）、0042（読者は自分の資格情報で読めた人）、0044（会話のアンカー）、H5

## 背景

0019 で、LINE 公式アカウントのチャネル（Webhook・シークレット・アクセストークン）は本体の手前の別システム（受け口）が持つと決めた。LINE は過去の会話を API で返さず、Webhook URL は 1 アカウントに 1 つだけなので、受け口が Webhook を受けて全部を貯める唯一の原本になる。本体はその利用者の 1 つ。

受け口には、もともと公式アカウントの機密を持ち、LINE の userId と人（従業員など）の紐づけを持っている業務システムを使える。業務システムはゲートウェイの上流サービス（API キーで読む GraphQL）として、すでにつながっている。

残る問いは 3 つ: 本体が原本をどう読むか（受け口から押すか、本体が引くか）、誰が読者か、送信をどう記録と観測の両方に乗せるか。

## 決定

### 1. 受け口が持つもの（受け口の側の仕様。本体はこれに依存する）

- Webhook のイベントを全部、組織ごとの原本として保存する。受信（Inbound）と、受け口から送ったもの（Outbound）の両方
- 差分読みの GraphQL のクエリ `lineEvents(after, since, first)`。保存の順のカーソル（固定長の UTC 時刻 + `|` + ID の文字列）で、`endCursor` を次の `after` に渡す。`since` はつないだ時刻から読み始めるため
- 送信の mutation `sendLineMessage(to, text, retryKey)`。push して、送ったものを原本に Outbound で残し、LINE の `sentMessages[].id` を返す
- 読む権限と送る権限は受け口のスコープで分ける（読むは本体とエージェント、送るはエージェント）

### 2. 本体は見回りで引く（受け口から押さない）

- 5 分ごとの見回り（`maintain`）で、`lineEvents` を前回のカーソルから読む（0041 の決定 1 と同じ）。1 回の見回りで 5 ページ（1 ページ 200 件）まで。超えたら次の見回りで続ける
- 押す形（受け口が本体の `/webhooks/*` に流す）にしない理由: 本体と受け口の間に新しい共有の秘密が要る、受け口が本体の宛先を知る必要がある、どちらかが落ちたときの取り直しを受け口に作ることになる。引く形なら、ゲートウェイの既存の資格情報（読者の API キー）だけで済み、取り直しはカーソルで本体が持つ
- 読む口は **GET の GraphQL だけ**（`GET /graphql?query=...&variables=...`。`src/connectors/line/scope.ts`）。受け口の GraphQL サーバは GET で mutation を受けない（HotChocolate の既定）ので、口で送信（`sendLineMessage`）は通らない。口の照合はパスだけなのでクエリの文字列は口では絞れず、本体が組み立てるのは `src/connectors/line/api.ts` の固定のクエリ（読めることの確かめと差分読み）だけにする。POST の口は持たない（本文の mutation を口で止められない）。本体は送信の口を持たない（0012）

### 3. 公式アカウント 1 つ = 共有リスト 1 つ。スペースは受け口の組織

- `spaceKey` は `line:<受け口の組織 ID>`。受け口の 1 組織に公式アカウントは 1 つ
- 窓口のアドレス（`selfAddresses`）は `{ channel: 'line', value: 'oa:<組織 ID>' }`。1 対 1 の受信はこの窓口宛て（リスト宛ての名指し。0038）で、受け口から送ったものはこの窓口から
- グループ・トークルームの受信は宛先なし（文脈だけ。0044 のグループの会話と同じで、リスト宛てにならない）。受け口はメンションを持たず、全部を名指しにすると人どうしの会話でリストが埋まるため。公式アカウントへのメンションを名指しにするのは、受け口がメンションを保存してから
- 担当は担当する操作（`ThreadClaimed`）。状態を持たない共有リスト（0033）なので、LINE は共有リストのいちばん素直な使い道になる
- 作れるのは、受け口でその組織のメッセージを読める人（スコープを持つ人）。サービスは管理者がデプロイの設定で許す（`MURMUR_SHARED_SERVICES` に `line`）

### 4. 読者は「自分の資格情報で受け口のメッセージを読めた人」（0042 の決定 4 と同じ）

- 受け口には「読める人の一覧」を返す口がない（ロールとスコープの組み合わせで決まる）。0042 と同じく、本人がつないで、本人のゲートウェイの資格情報で `lineEvents` が読めた人を読者に足す
- 見回りで 60 分ごとに、読者それぞれの資格情報で読めるか確かめ直し、読めない人を外す。取り込みに使う資格情報が読めなくなったら、読める読者の 1 人に入れ替える。誰も読めなければ broken
- 読めることの確かめは `myOrganization { id name }` と `lineEvents(first: 1)` を 1 回。組織が違う資格情報（別の組織の API キー）は、その共有リストの読者にしない
- 名乗りのアドレスは `{ channel: 'line', value: 'bm-next:<組織 ID>:<トピック索引の User ID>' }` にする（LINE の userId ではない。読者は公式アカウントの中の人で、LINE の友だちではない）。受け口には「本人のメンバー」を返す口がないので、受け口の組織とトピック索引の User の組で 1 人に 1 つ。窓口から送ったものは窓口のアドレスなので、名乗りのアドレスがシグナルに出ることはない
- 読めないことは、受け口の認可の失敗（`AUTH_NOT_AUTHORIZED` など）と 401・403 で知る。一時的な失敗（ゲートウェイ・受け口の障害）では読者を減らさない

### 5. メッセージの写し方

- **相手のアドレス**は `{ channel: 'line', value: <LINE の userId> }`。受け口が付けた表示名とメンバー名は使わない（Contact はエージェントが作る。0030・0035）。ただし未解決のアドレスの候補として名前を出せるよう、本文の先頭には付けない
- **区切り**: 会話のアンカー（0044）を使う。`conversationId` は 1 対 1 なら相手の userId、グループ・トークルームなら groupId / roomId。`conversationGroup` はグループ・トークルームで真。同じ相手との話題ごとに AI がトピックを分け、別の相手のメッセージが同じトピックに入ることはない
- **アンカー**: `messageId` は LINE のメッセージ ID（受信）と送ったメッセージの ID（送信）。引用返信は `quotedMessageId`
- **送信**: Outbound は窓口から相手宛ての観測された送信。`messageId` が `record_sent` の `sent_ref`（`sentMessages[].id`）と同じなので、記録と観測が 1 つになる（H5。どちらが先に届いても）
- **取り込むイベント**: テキスト・画像・動画・音声・ファイル・位置・スタンプのメッセージと、postback（リッチメニューのボタン）。テキスト以外は本文を「[画像]」のような印にする（中身は受け口から読む）。友だち追加・ブロック・既読などは取り込まない
- グループで userId の取れないメッセージは取り込まない（送り主が決まらない）
- つなぐ前に保存されたイベントは取り込まない（`since` をつないだ時刻にする。0041 と同じ）

### 6. 管理画面から返した分は見えない

LINE の仕様で、公式アカウントの管理画面（Official Account Manager）のチャットから返した分は Webhook に来ず、受け口の原本にも入らない（0019 の調べ）。トピック索引に返事を残したいなら、返事はエージェント（受け口の送信）から送る。管理画面で返したトピックは、人が担当を外すか片付ける。

## 代案

- **受け口が本体の Webhook に押す**: 遅れはなくなるが、共有の秘密と取り直しの仕組みが要る（決定 2）。トピック索引の用途では 5 分の遅れで足りる（0042 と同じ判断）
- **本体が LINE の Webhook を直接受ける**: 0019 で退けた（機密を本体に入れない、userId と人の紐づけは受け口の仕事）
- **POST の GraphQL を口に入れる**: 本文の mutation を口で止められない。GET に限れば、受け口のサーバの側で mutation が通らない
- **読者を受け口のロールから写す**: ロールとスコープを読む口を本体に足すことになり、読める人の判定が受け口の権限の仕組みに依存する。0042 と同じ「読めた人」で足りる

## 帰結

- 受け口の組織の API キーを、ゲートウェイの受け口のサービス（既定 `bm-next`。デプロイの設定 `MURMUR_BM_NEXT_SERVICE` で変えられる）に登録した人だけがつなげる
- スタンドの送信は受け口のスキルで `sendLineMessage` を呼び、すぐ `record_sent`（`data_source` は LINE の共有リスト、`to` は相手の userId、`sent_ref` は返った `messageId`、`anchors.conversation_id` は相手の userId）
- 管理画面での返事は見えない（決定 6）ので、LINE の返事待ち（`awaiting`）は、エージェントから送ったものだけ

## 実物で確かめること

- 受け口の GraphQL サーバが GET のクエリを受け、GET の mutation を断ること（GET の CSRF 対策で断られる場合に備え、`GraphQL-Preflight: 1` を付けて送る）
- ゲートウェイの受け口のサービス（`bm-next`）が GET の `/graphql` をそのまま中継すること
- 受け口の Webhook の疎通（LINE Developers の「検証」）と、受信・送信が `lineEvents` に出ること
- `record_sent` と観測された送信が 1 つになること（H5）
