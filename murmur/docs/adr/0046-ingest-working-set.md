# 0046 取り込みは投影の全件ではなく、区切りに要る範囲だけを読む

- 状態: 採用（2026-11-18、直樹）。実装は進める順番の 1〜3 まで（末尾の「実装の記録」）。4（実データで確かめる）はデプロイのあと
- 関連: 0001（FC-IS）、0009（区切りの 4 段）、0014（スレッドの 1 種類・fold は 1 段）、0021（D1・投影を差分で書く）、0031（状態の写し）、0038（担当と名指し）、0044（会話のアンカー）、H1・H6

## 背景

投影（threads・signals・索引）は、コマンドのたびに全件を読み込んでコアに渡している（`MurmurService.state()`）。fold と保存はもともと差分だけで、重いのは読み込み。取り込みの 1 件ごと（重複でも）、API の 1 回ごと、見回りの仕事ごとに全件を読むので、D1 の rows_read は「投影の行数 × 呼ぶ回数」で増える。

あるデプロイ（トピック 300 本・メッセージ 550 通ほど、つないで 2 週間）で、D1 の無料枠（1 日 500 万行）の 79% に達した。rows_read の 98% が投影とマスタの全件の select（1 日あわせて 1 万 4 千回）だった。Jira の差分の重なり読み（0034 の決定 3）や共有リストの見回りで、重複と判定されるだけの取り込みが多く、その 1 件ごとに全件を読んでいた。

2026-11-18 に、isolate の中に投影とマスタの写しを持ち、版の 1 行だけ確かめるようにした（`src/store/d1.ts`。0021 の実装の範囲）。温まった isolate では読む行がほぼなくなるが、冷えた isolate（Cron・Queue・API の起動が当たる先）では全件を読み、その量はデータに比例して増え続ける。イベントは 2 週間で 1,600 件ほどなので、1 年でメッセージは数万通になり、冷えた isolate の全件の読み込みが 1 日 100 回を超えたあたりで、写しがあっても無料枠に届く。

ところが、取り込みの判断が実際に見ているのはごく一部である。

| 段（`planThreading` ほか） | 何で決めるか | 判定 | 今の読み方 |
| --- | --- | --- | --- |
| 重複（`prepareInbound`） | `sourceRef` | 機械的 | 索引（`projection_meta.idx` の 1 行）。記録との統合は `messageId` で引いたシグナル 1 通 |
| 写しの置き先（`planMirror`・`threadOfSourceKey`） | 課題キー・タスクの ID（`threadKey`・`sourceKey`） | 機械的 | 同じデータソースの全シグナルと全スレッドを走査 |
| 1. アンカー（`resolveAnchors`） | `threadKey`・`In-Reply-To`・引用・`threadTs` | 機械的 | 全シグナルを走査（`messageId` は索引） |
| 2. 返事待ち（`awaitingThread`） | 同じ相手に返事を待っているスレッドが 1 本だけ | 機械的 | 全スレッドを走査 |
| 3. 直近の候補（`recentThreads`）→ AI | 同じ相手の直近 5 本から、AI が続きか新しいスレッドかを選ぶ | AI | 全スレッドを走査して並べ替え |

全件が要るように見えたのは、機械的に引けるもの（重複・写し・1・2）を「全部並べて探す」書き方にしていたからで、区切りの性質として全件は要らない。全件に意味がありそうなのは AI に選ばせる 3 だけで、そこも実務では直近のものを見れば足りる。古いスレッドの続きが新しいスレッドになっても、AI の判断がずれたときと同じ程度の害で、人が `move_signal` で直せる。

fold は 1 段で（0014）、スレッドの再計算（`recompute`）はそのスレッドのログだけで決まる。足りないスレッドに触れば `mustThread` が例外になる。したがって、触るスレッドとシグナルが入っていれば、部分的な投影の上で畳んでも結果は全件の上で畳んだときと同じになる。

## 決定（案）

### 1. 取り込みは「作業範囲」の投影で判断し、畳む

取り込み（`ingest`・`mirror`）は、シェルが組み立てた**作業範囲**（部分的な `Projections`）をコアに渡す。コアの関数（`prepareInbound`・`planMirror`・`planThreading`・`fold`）は変えない。作業範囲が「判断に要るものを全部含む」ことをシェルが保証し、コアは受け取った範囲の中で今までどおり決める。

作業範囲は段ごとに読む。前の段で決まれば、後の段は読まない。

1. **重複**: `sourceRef` の索引を主キーで 1 行引く。あれば終わり（`duplicate`）。記録との統合（`merged`）は `messageId` の索引で引いたシグナル 1 通
2. **写しの置き先**: `threadKey`・`sourceKey` の索引で引いたスレッド 1 本。「変わっていない」（`unchanged`）ならそこで終わり
3. **アンカー**: シグナルのアンカーの値（`threadKey`・`inReplyTo`・`quotedMessageId`・`threadTs`）を索引で引き、当たったシグナルとそのスレッド
4. **返事待ち**: 同じデータソースで、外していない名指しが残っているスレッドの全部（返事待ちの上位集合。窓で切らない。決定 3）
5. **直近の候補**: 同じデータソースで、最後のシグナルが窓（決定 4）の中にあるスレッドと、そのシグナル

区切りが決まったら、追記したイベント（`SignalObserved`・`SignalThreaded`・`ThreadMirrored`）を作業範囲の上で畳み（`foldChanges`）、変わった行だけ保存する（今と同じ）。置き先のスレッドは作業範囲に入っている（段 2〜5 で読んだか、新しく作る）。

### 2. 索引を行のテーブルにする

`projection_meta.idx`（`sourceRefs`・`messageIds` の JSON 1 行。いまで 115 KB、件数に比例して増え、いつか 1 行 2 MB の上限に当たる。0021 の 4）をやめ、行のテーブルにする。

- `signal_keys(data_source_id, kind, value, signal_id)`、主キー `(data_source_id, kind, value)`
  - `kind`: `sourceRef`・`messageId`・`threadKey`・`threadTs`
  - fold が書く（今の索引と同じく、イベントだけから決まる。投影なのでいつでも作り直せる）
- `threads` に列を足す（どれも fold がスレッドのログから決める。マスタに依存しない）
  - `source_key`（写しのスレッド。0031 の 8）
  - `last_signal_at`（最後のシグナルの時刻。向きは問わない）
  - `named_pending`（外していない名指しが 1 つでも残っている。`attention.named` が空でない）。向き（こちらからか）と読者はクエリ層がそのときのマスタで決めるので（0030）、fold が持てるのはこの上位集合まで
  - 3 つに索引（`(data_source_id, source_key)`・`(data_source_id, last_signal_at)`・`(data_source_id) WHERE named_pending`）
- `ProjectionChanges.index` は、変わった索引の行（足した行）を持つ形にする。索引の行は消えない（スレッド・シグナルと同じ）

`threadTs` の照合（`resolveAnchors` の「`messageId` か `threadTs` が一致」）は、`messageId` と `threadTs` の 2 つの `kind` を引けば足りる。

### 3. 返事待ちは窓で切らない

段 2（`awaitingThread`）は「返事を待っているスレッドが **1 本だけ** なら」で決める。窓で切ると本数が変わり、2 本のうち 1 本が窓の外に出ただけで、残った 1 本に寄せてしまう。上位集合（`named_pending`）を全部読み、本当に返事待ちか（こちらからの送信の宛先か、読者でない相手か、まだ発言していないか）はコアが今までどおり決める。

上位集合には、読んだまま外していない受信（FYI のメールなど）も入る。名指しは外すまで残る（0038）ので、外さない運用だと少しずつ増える。それでも「全スレッド」ではなく「外していない名指しのあるスレッド」で、本人が外せば減る。増えすぎたときは、上位集合だけ長い窓（たとえば 180 日）で切る（未決 4）。

### 4. AI に渡す候補だけ、窓で切る

段 3（`recentThreads`）は、同じデータソースで `last_signal_at` が窓の中にあるスレッドから選ぶ。

- 窓の既定は 30 日（`IngestPolicy` に足す。デプロイで変えられる）。それでも多いときに備えて、新しい順に上限（既定 200 本）で切る
- 相手が同じか（`withSameCounterpart`）、会話が同じか（0044 の `conversationId`）、直近 5 本に絞るのは、コアが今までどおり行う
- 窓の外のスレッドの続きは、新しいスレッドになる（「アンカーも返事待ちも直近のスレッドもない」）。これを受け入れる。機械的に引けるもの（アンカー・課題キー・返事待ち）は窓の外でも正しく当たる

`lastActivity`（候補の並び）は向きを読者で決める（`commView`）ので、列の `last_signal_at` は窓で絞るのにだけ使い、並びはコアが今までどおり決める。

### 5. 作業範囲の追いつき

作業範囲は、保存済みの投影の lastSeq の時点のもの。追記されたのに保存されていないイベント（保存が弾かれた・失敗した）があれば、今のように全件を読んで追いついてから（`state()`）作業範囲を読む。めったに起きない。追記の楽観ロック（0021）はそのまま。競合したら作業範囲を読み直してやり直す。

### 6. 取り込みのほかは今のまま

一覧と詳細（`list_threads`・`get_thread`。可視性・担当・名指し・結んだ先の様子を全スレッドで出す）、人とエージェントの操作（担当・結ぶ・移す・片付け・メモ）、期限の見回り（`checkOverdue`）、作り直し（`rebuild`）は、今までどおり投影の全件（isolate の写し）を使う。呼ぶ回数が取り込みよりずっと少ないので、まず取り込みだけを変える。一覧を窓や「開いているもの」で絞るかは、別に決める（未決 2）。

## 代案

- **写し（isolate のキャッシュ）だけで済ませる**: 温まった isolate ではほぼ 0 行になるが、冷えた isolate の全件はデータに比例して増え続ける。作業範囲と組み合わせる（写しはそのまま残す）
- **Durable Object に移し、投影をメモリに持つ**（0021 のもう 1 つの候補）: `load()` がほぼ消え、読み取りの行数の問題はなくなる。ただ、サービスの層を Durable Object の中に移す大きな移行になり、投影を全部メモリに持つ前提もデータに比例して重くなる。作業範囲は Durable Object に移すときにも効く（メモリに全件を持たなくてよくなる）ので、先にこちらを入れる
- **全部の段を窓で切る**: 実装は簡単だが、久しぶりに動いた課題・タスク（写し）が別のスレッドになり、同じ課題キーのスレッドが 2 本できる。窓の外で返事が来ると、返事待ち・期限超過が元のスレッドに残り続ける。機械的に引けるものは索引で正確に引けるので、窓で切る理由がない
- **コアの関数を、範囲を読む口（ポート）を受け取る形に書き換える**: コアが必要なものを都度問い合わせる形。FC-IS（0001）を崩す（コアが非同期の IO を持つ）。作業範囲をシェルが先に組み立てれば、コアは純関数のままで済む

## 帰結

- 取り込み 1 件で読む行は、重複なら 1 行、写しの「変わっていない」なら数行、新しいメッセージでも「アンカーの行 + 返事待ちのスレッド + 窓の中のスレッドとそのシグナル」で、データの総量ではなく直近の量と待ちの数で決まる
- 窓の外のスレッドの続きは、AI の候補に出ず新しいスレッドになる。H6（区切りの一致率）の記録は、窓の中の候補で取り直す（窓の既定で一致率が落ちないかを、記録・再生のシナリオで確かめる）
- 索引が行になり、`projection_meta.idx` の 2 MB の上限（0021 の 4）がなくなる
- 作業範囲が判断に要るものを含むことは、シェルの責任になる。取りこぼすと、全件のときと違う判断（新しいスレッド）になっても例外にならない。H1 のリプレイ（全件の fold と、作業範囲で取り込んだ結果の一致）と、全シナリオで「作業範囲で判断しても全件で判断しても同じ」を確かめるテストを足す（窓の外に出る候補だけは、窓を十分大きくして比べる）
- マイグレーションが要る（索引のテーブルと列。投影なので作り直しで埋める）

## 進める順番

1. 索引を行のテーブルにし、列を足す（決定 2）。fold と保存を直し、作り直しで埋める。この段では、まだ全件を読む（結果が同じことを H1 で確かめる）
2. 重複と写しを索引で引く（決定 1 の段 1・2）。これだけで、重なり読みの重複がほぼ 1 行になる
3. アンカー・返事待ち・窓の候補（決定 1 の段 3〜5、決定 3・4）。H6 の記録を窓の中で取り直す
4. 実データで rows_read を確かめる

## 未決

1. 窓の既定（30 日）と上限（200 本）。メールの往復の間隔と、データソースごとの量を見て決める
2. 一覧（`list_threads`）を作業範囲のように絞るか。「自分のタスク」は開いているものと名指しの残っているものだけで足りるが、`filter=all` や結んだ先の様子は全件を見る
3. 期限の見回り（`checkOverdue`）を、返事の期限のあるスレッドだけ読む形にするか（`threads` に期限の列を足せば引ける）
4. 返事待ちの上位集合（`named_pending`）の大きさ。実データで数え、外さない名指しで増えすぎるなら、上位集合だけ長い窓で切る（切った窓の外に返事待ちが残っていると「1 本だけ」の数え方が変わるので、窓は返事の往復よりずっと長くする）

## 実装の記録（2026-11-18）

- **索引**（決定 2）: `signal_keys` と `threads` の 3 列は、保存先がシグナルとスレッドの記録から作る（`src/domain/working-set.ts` の `signalKeysOf`・`threadColumns`。fold は変えていない）。全件の読み込みでは、索引を `projection_meta.idx` からではなくシグナルから作り直す（`indexOfSignals`。fold が積むのと同じ）。`idx` の列は 0046 より前のコードのために残し、もう書き換えない（新しく作る行には空の索引）。デプロイの切り替えの間に古いコードが動くと、古い `idx` で重複を判定するので、その間に届いた同じものを二重に取り込みうる（数秒の窓。消すときはマイグレーションで列を落とす）
- **マイグレーション**（`drizzle/0004_ingest_working_set.sql`）: 表と列を足し、既存の行の JSON から列と索引を埋める（Worker で作り直すと、1 回の実行のクエリ数の上限に当たるため）。`named_pending` は SQL では「名指しが 1 つでもある」で埋める（外した位置の比べ方を SQL に持ち込まない。上位集合なので安全）。次にそのスレッドを保存したときに正確な値になる。マイグレーションのあと新しいコードに切り替わるまでの間に古いコードが書いた行には索引ができないので、切り替わってから埋める文をもう一度流す（何度流しても同じ結果。申し送りのデプロイの手順）
- **意味**（決定 1）: 依頼は `dedupeRequest`・`threadingRequest`・`mirrorRequest`、範囲の意味は `selectWorkingSet`（全件から選ぶ純関数）。メモリの保存先はこれを使い、D1（`D1ProjectionStore.workingSet`）は 3 回の往復で同じものを引く。両者の一致は全シナリオの全シグナルの依頼で確かめている（`test/shell/working-set.test.ts`）
- **取り込みの流れ**: `ingest` は、まず重複排除の依頼で `prepareInbound` を呼び（ID は使わない。採番がずれるため）、重複・統合ならそこで終える。そうでなければ区切りの依頼で読み直し、`run()` の中で重複排除からやり直す（間に別の書き手が同じものを取り込んでいても重複と分かる）。`mirror` は写しの依頼で読む。作業範囲の上で畳んだものは `save(…, { partial: true })` で、変わった行だけ書き、isolate の写しにはしない（写しは次の `load` で追記から追いつく）。メモリの保存先は、部分的な索引で全体を置き換えないよう、索引を足し込む
- **全件に戻すとき**（決定 5）: 保存先が作業範囲を持たない、保存済みの lastSeq より先のイベントがある、投影の形が古い（`isStaleProjections`）なら `state()` を使う。追いつきの確かめに、取り込み 1 件ごとに `events.seq > lastSeq` の select（ふつう 0 行）が 1 本増える
- **窓**（決定 4）: `IngestPolicy` に `candidateWindowDays`（30）と `candidateWindowLimit`（200）を足した。デプロイの設定から変える口はまだない（`feature.ts` は既定を使う）
- **H6**: 4 シナリオの時刻は窓の中に収まるので、記録した AI の判断はそのまま再生でき、一致率は変わらない（記録は取り直していない）
- **テスト**: `test/shell/signal-keys.test.ts`（差分の保存・作り直し・マイグレーションの行がイベントからの fold と一致）、`test/shell/working-set.test.ts`（D1 と `selectWorkingSet` の一致、冷えた isolate で重複・写し・新しいメッセージのどれでも threads と signals の全件の select がない）。メモリの保存先が作業範囲を使うので、既存のテストとシナリオは全部この経路を通る
