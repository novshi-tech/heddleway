# 0003 手元や顧客の環境のサービスへは、逆向きの接続で届く

- 状態: 採用(2026-11-23、直樹とのディスカッション。案は 2026-10-29)。2026-11-23 に、使い道を boid から業務特化のコンテナに広げ、Cloudflare Tunnel の段階を取り下げた(下の「改訂」)。実装はこれから
- 関連: [0001](0001-absorb-boid-gateways.md)、[0008](0008-narrow-grants-for-apps.md)(アプリには絞った許可を出す)、[background-access.md](../background-access.md)、README の `identity` の認証方式
- 発端: novshi-tech/boid の `docs/plans/split-and-shrink.md` §4

## 背景

ゲートウェイから届けたいのに、外から入口を開けられない場所でサービスが動くことがある。

- **業務特化のコンテナ**。API のないレガシーシステムを自動化するために、Chromium と Playwright を入れたコンテナを立てる。コンテナは「受注を登録する」「在庫を調べる」のような、その業務でできる操作だけを API として出し、内側でブラウザを動かす。Claude はゲートウェイ経由でこの API を呼ぶ
  - 最初は、boid が動いている開発用の PC の中で動かす
  - 将来は、顧客の Azure の AKS の Pod の中で動かし、本番の環境の調査などをさせたい。環境ごとに、できる操作を API に閉じ込められるのが大きい
- **boid**。縮退後の boid は workspace・sandbox・job だけを持つ実行環境になり、オーケストレータ役のスタンドがゲートウェイ経由で job の API を呼ぶ。boid も手元の PC で動く

どちらも、手元の PC や顧客のクラスタに外からの入口を開けたくない。Murmur のように Service Binding で結ぶこともできない。

## 決定

### 1. 逆向きの接続先を、接続先の定義の 1 種類として足す

手元のサービスのほうからゲートウェイにつなぎに行き、ゲートウェイが中継する。

- 手元のサービスが、ゲートウェイの Durable Object に WebSocket の接続を張りっぱなしにする。ゲートウェイは、その接続先へのリクエストを WebSocket に載せて中継する
- 手元の側は外へのつなぎだけで済み、入口を開けなくてよい。顧客のクラスタでも Ingress を足さずに済むので、顧客の側の承認も通りやすい
- **boid 専用にしない**。業務特化のコンテナも boid も、同じ「逆向きの接続先」として登録する
- 中継の動き(ヘッダーの注入、ボディの素通し、操作ログ)は REST の接続先と同じものを使う。ゲートウェイは HTTP と OAuth2 だけを知る、という性格を崩さない
- 認証方式は `identity` と組み合わせる。ゲートウェイはサインイン中のユーザーの ID を署名した JWT を中継のリクエストに載せ、手元のサービスは誰の依頼かを確かめ、受け付ける `sub` を絞れる

### 2. 登録はデプロイごとに、管理者が行う

- 逆向きの接続先は、管理画面で管理者だけが登録する
- 開発用の PC の boid や業務コンテナはノブシテックのデプロイに、顧客の AKS のコンテナはその顧客のデプロイに登録する([0004](0004-one-deployment-per-organization.md) の 1 つのデプロイ = 1 つの組織に乗る)
- ユーザーごとの逆向きの接続先は、当面持たない

### 3. つなぎに来るときの資格は、接続先ごとのシークレットにする

- 管理者が管理画面で接続先ごとにシークレットを発行する。手元の側は、それを持って WebSocket の接続を張る
- 取り消しと発行し直しも管理画面からできる。取り消したら、張られている接続も切る
- Pod なら k8s の Secret に入れるだけで済む。OAuth のクライアントにする案は、人の同意が要るので Pod と相性が悪く、採らない

### 4. 長い処理は非同期にし、それをサービスの側の API の約束にする

- ブラウザの操作は数十秒から数分かかる。ゲートウェイが長いリクエストを抱えたまま中継するのではなく、サービスの側が非同期の API を出す
  - job を投げると `202` と ID を返す。状態と結果は `GET` で取りに行く
- ゲートウェイは、1 回ずつの短い HTTP のリクエストを中継するだけ。非同期かどうかを知らない
- boid の job の API も同じ形なので、そのまま乗る

### 5. 手元のサービスは、できる操作を API に閉じ込める

- 逆向きの接続は「チャットから手元や顧客の環境の中に入れる口」になる。サービスの側は、届いたリクエストを自分の範囲(業務の操作、boid なら job の API)に絞る
- 逆向きの接続を、任意のホストへの中継(汎用のトンネルや SOCKS)にしない
- アプリ(heddleway-dispatcher など)から呼ばせるときは、[0008](0008-narrow-grants-for-apps.md) の絞った許可で、呼べる口をさらに絞る

## 条件・リスク

- オーケストレータや Claude を通る結果は、そのアカウントの Claude に入る。顧客の本番の環境を調べる業務コンテナは、返す結果(要約にとどめる、個人の情報を出さない)を API の約束で絞る
- 手元の側が落ちている・つながっていないときは、ゲートウェイはすぐにエラー(`503` など)を返す。待たせない

## 代案

- **Cloudflare Tunnel で公開し、その URL を `identity` の接続先の `base_url` にする**: ゲートウェイのコードを変えずに始められるので、案ではこれを最初の段階にしていた。手元に入口を開けること、Tunnel の設定が手元ごとに要ること、顧客のクラスタでは使いにくいことから、取り下げた(下の「改訂」)
- **boid を Cloudflare の Worker にする**: boid の価値は手元の実行環境(コンテナ、workspace の永続化)にあり、Worker にはできない
- **業務コンテナを boid の job として動かす**: 業務コンテナは常駐して API を出すもので、使い捨ての job とは形が違う。顧客の AKS では boid がない。独立したコンテナにする

## 未決

1. Durable Object の WebSocket(ハイバネーション)で、大きいボディ(スクリーンショット・ダウンロードしたファイル)をどこまで中継できるか。上限を超えるものの返し方
2. 同じ接続先に複数のインスタンス(Pod のレプリカ)がつないだときの扱い(1 つだけ許すか、振り分けるか)
3. 非同期の API の約束(job の投げ方、状態の名前、結果の取り方)を、業務コンテナと boid で共通の形にするか。共通にするなら、どこに書くか
4. 操作ログに、非同期の job の ID をどう残すか(投げた人と結果を取った人をつなぐ)

## 改訂(2026-11-23): 使い道を業務コンテナに広げ、Tunnel の段階を取り下げる

- 案は boid を接続先にすることが出発点で、決定 1 を「boid を `identity` の接続先にし、最初は Cloudflare Tunnel で公開する」、逆向きの接続を構想の決定 2 にしていた
- 業務特化のコンテナ(Playwright でレガシーシステムを操作する、将来は顧客の AKS で本番の調査をする)という使い道が増え、逆向きの接続が本命になった。Tunnel の段階を飛ばし、最初から逆向きの接続で作る
- 案の未決のうち、資格の形(→ 決定 3)と、ユーザーごとかデプロイで 1 つか(→ 決定 2)を閉じた。長いリクエストの中継は、非同期をサービスの側の約束にすること(→ 決定 4)で、ゲートウェイの課題ではなくした
