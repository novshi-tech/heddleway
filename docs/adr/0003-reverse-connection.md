# 0003 手元や顧客の環境のサービスとは、所有者の決まったトンネルでつながる

- 状態: 採用(2026-11-23、直樹とのディスカッション。案は 2026-10-29)。2026-11-23 に、使い道を boid から業務特化のコンテナに広げ、Cloudflare Tunnel の段階を取り下げ、接続ごとに所有者を決めて手元からの呼び返しを足した(下の「改訂」)。段階 1〜3(ペアリングと鍵での接続、呼び返し、厳しめのモード)を実装した(下の「実装のメモ」)
- 関連: [0001](0001-absorb-boid-gateways.md)、[0008](0008-narrow-grants-for-apps.md)(アプリには絞った許可を出す)、[background-access.md](../background-access.md)、README の `identity` の認証方式
- 発端: novshi-tech/boid の `docs/plans/split-and-shrink.md` §4

## 背景

ゲートウェイから届けたいのに、外から入口を開けられない場所でサービスが動くことがある。

- **業務特化のコンテナ**。API のないレガシーシステムを自動化するために、Chromium と Playwright を入れたコンテナを立てる。コンテナは「受注を登録する」「在庫を調べる」のような、その業務でできる操作だけを API として出し、内側でブラウザを動かす。Claude はゲートウェイ経由でこの API を呼ぶ
  - 最初は、boid が動いている開発用の PC の中で動かす
  - 将来は、顧客の Azure の AKS の Pod の中で動かし、本番の環境の調査などをさせたい。環境ごとに、できる操作を API に閉じ込められるのが大きい
- **boid**。縮退後の boid は workspace・sandbox・job だけを持つ実行環境になり、オーケストレータ役のスタンドがゲートウェイ経由で job の API を呼ぶ。boid も手元の PC で動く

どちらも、手元の PC や顧客のクラスタに外からの入口を開けたくない。Murmur のように Service Binding で結ぶこともできない。

逆の向きも要る。claude.ai のカスタムコネクタは、ゲートウェイへの OAuth のトークンを提供元の側で持ってくれるので、手元には何も残らない。Gemini のように提供元のカスタムコネクタがないハーネスを手元で動かすと、全部のサービスに届くゲートウェイのトークンが手元のファイルに残る。ローカルサービスからゲートウェイを呼ぶ道を、同じ接続の中に用意したい。

## 決定

### 1. ローカルサービスを、接続先の定義の 1 種類として足す

ローカルサービスのほうからゲートウェイにつなぎに行き、ゲートウェイが中継する。

- ローカルサービスが、ゲートウェイの Durable Object に WebSocket の接続を張りっぱなしにする。ゲートウェイは、その接続先へのリクエストを WebSocket に載せて中継する
- 手元の側は外へのつなぎだけで済み、入口を開けなくてよい。顧客のクラスタでも Ingress を足さずに済むので、顧客の側の承認も通りやすい
- **boid 専用にしない**。業務特化のコンテナも boid も、同じ「ローカルサービス」として登録する
- 中継の動き(ヘッダーの注入、ボディの素通し、操作ログ)は REST の接続先と同じものを使う。ゲートウェイは HTTP と OAuth2 だけを知る、という性格を崩さない

### 2. 接続ごとに所有者を 1 人決める

- ローカルサービスは、どれも 1 人のユーザーの持ち物にする。boid は 1 つの daemon に 1 人の所有者がいるパーソナルなエージェントで、業務コンテナもレガシーシステムのログインが誰かのものなので、結局は人に紐付く
- **呼べるのは所有者だけ**。ほかの人が呼べると、その人が所有者の認証情報で動くことになる(混乱した代理人)
- 呼び返し(決定 5)も、いつも所有者として動く。どのユーザーのコンテキストかを、呼び出しごとに決める仕組みは持たない
- 複数のユーザーで共有するものは、ローカルサービスではなくアプリ([0008](0008-narrow-grants-for-apps.md))で作る

### 3. 登録は所有者のペアリングで行う

- ローカルサービスがペアリングのコードを出し、所有者がゲートウェイの画面で承認する。コードは 5 分で切れ、1 回だけ使える(今の boid の Web UI のペアリングと同じ)
- 管理者の承認は挟まない。Heddleway から手元への呼び出しは所有者だけのものなので、所有者が自分のマシンを自分に開くことになる。所有者は今でも自分の認証情報で Claude やスクリプトからデータを持ち出せるので、組織から見て新しく増える脱出口はほとんどない
- 管理者は、デプロイのすべてのローカルサービスの一覧を見て、取り消し、所有者を付け替えられる(所有者が退職したときなど)。デプロイの設定で、ペアリングと呼び返しをそれぞれ禁止できる。顧客のデプロイでは、管理者が締められる
- 所有者は「アクセスを許可したアプリ」の画面で、自分の接続先と最後につないだ時刻を見て、取り消せる

### 4. 身元の証明は接続を張るときだけ行い、接続をセッションにする

- ペアリングのとき、ローカルサービスが鍵ペアを作り、ゲートウェイには公開鍵だけを登録する。つなぐときは、ゲートウェイが出す値に秘密鍵で署名して証明する。ゲートウェイの側に、漏れて困るシークレットを置かない
- つながっているあいだは、接続そのものがセッションになる。ゲートウェイは、そのソケットがどの所有者のどの接続先かを知っているので、呼び出しごとのトークンは要らない
- WebSocket は、スリープ、ネットワークの切り替え、手元の再起動、**ゲートウェイのデプロイ**(Durable Object のコードが入れ替わると、張っている WebSocket はすべて切れる)で切れる。再接続の証明は 2 つのモードから選ぶ
  - **標準**: 秘密鍵をローカルサービスの保存場所(boid なら daemon の volume、0600)に置き、いつでも自動でつなぎ直す
  - **厳しめ**: ディスクに鍵を置かない。つながっているあいだにゲートウェイが短命の再開トークンを渡して入れ替え、手元はメモリにだけ持つ。瞬断やデプロイからは戻れるが、手元の再起動や長いスリープのあとは、所有者がペアリングし直す。顧客の環境のように、ディスクに鍵を置きたくないところ向け

### 5. 手元からゲートウェイを呼び返せる。範囲は所有者がサービス単位で選ぶ

- 同じ接続の中で、ローカルサービスがゲートウェイの中継(`/api/<service>/...`)を所有者として呼べる。Gemini のように提供元のカスタムコネクタがないハーネスでも、全部のサービスに届くゲートウェイのトークンを手元のファイルに置かずに済む
- **初期値は呼び返しなし**。所有者がペアリングのとき(とあとから画面で)、呼び返せるサービスにチェックを付ける(「freee と Graph だけ」)。パスまでは絞らない
- **鍵はエージェントに見せない**。鍵を持つのは、エージェントではない手元のプロセス(boid の daemon、業務コンテナのプロセス)だけ。boid は、サンドボックスにゲートウェイ用の中継口だけを出し、エージェントはそこに REST を投げる。daemon がそれを WebSocket に流す。サンドボックスには鍵もトークンも入れない
  - boid の daemon は中継口で、workspace ごとに呼び返しを絞れる(顧客の workspace からは禁止、など)。job の ID を付けて流せば、操作ログに残せる
  - この中継口はサービスの認証情報を持たず、ゲートウェイに流すだけ。認証情報の置き場をゲートウェイに一本化する [0001](0001-absorb-boid-gateways.md) とはぶつからない

### 6. 長い処理は非同期にし、それをサービスの側の API の約束にする

- ブラウザの操作は数十秒から数分かかる。ゲートウェイが長いリクエストを抱えたまま中継するのではなく、サービスの側が非同期の API を出す
  - job を投げると `202` と ID を返す。状態と結果は `GET` で取りに行く
- ゲートウェイは、1 回ずつの短い HTTP のリクエストを中継するだけ。非同期かどうかを知らない
- boid の job の API も同じ形なので、そのまま乗る

### 7. ローカルサービスは、できる操作を API に閉じ込め、エージェント向けの説明を送る

- トンネルは「チャットから手元や顧客の環境の中に入れる口」になる。サービスの側は、届いたリクエストを自分の範囲(業務の操作、boid なら job の API)に絞る。ゲートウェイは手元の API の定義(口の一覧)を持たない
- トンネルを、任意のホストへの中継(汎用のプロキシや SOCKS)にしない
- ローカルサービスは、つないだときにエージェント向けの説明(何ができるか、どう呼ぶか)を送る。ゲートウェイはそれを接続先の一覧に出し、エージェントが読む。説明はいつもローカルサービスの今の版になる

## 条件・リスク

- **呼び返しの範囲はサービス単位で粗い**。Graph はメールも予定表もファイルも 1 つのサービス。秘密鍵が漏れると、選んだサービスに所有者として、取り消すまで届く。対策は取り消しと、最後につないだ時刻の表示。個人の boid はこれで足り、顧客の環境は管理者が締める(決定 3)か、厳しめのモード(決定 4)にする
- 残るのは、手元のホストそのものが乗っ取られた場合。これは何を置いても同じなので割り切る
- オーケストレータや Claude を通る結果は、そのアカウントの Claude に入る。顧客の本番の環境を調べる業務コンテナは、返す結果(要約にとどめる、個人の情報を出さない)を API の約束で絞る
- ローカルサービスが送る説明は、エージェントにとっては所有者のサービスが書いたテキスト。指示としてではなく、使い方の情報として読む
- 手元の側がつながっていないときは、ゲートウェイはすぐにエラー(`503` など)を返す。待たせない

## 代案

- **委任**(依頼ごとに「誰として・どの接続先が・いつまで・何を呼び返せるか」を作り、呼び返しをその中に閉じる): 複数のユーザーが 1 つのローカルサービスを使う形にも広げられるが、作成・延長・終了と、委任の起こし方(中継に乗るか、人が直接起こすか)が要り、複雑になる。いまの接続先はどれも 1 人のもので、共有するものはアプリで作れるので、採らない。所有者のモデルは「委任がいつも所有者から開いている」特別な形なので、要るようになったら上に積める
- **管理者が登録し、接続先ごとのシークレットで証明する**: 案の段階ではこうしていた。所有者が 1 人に決まるので、管理者の承認より所有者のペアリングのほうが合う。シークレットの文字列はゲートウェイの側にも漏れて困るものが残るので、鍵ペアにした
- **Cloudflare Tunnel で公開し、その URL を `identity` の接続先の `base_url` にする**: ゲートウェイのコードを変えずに始められるので、案ではこれを最初の段階にしていた。手元に入口を開けること、Tunnel の設定が手元ごとに要ること、顧客のクラスタでは使いにくいことから、取り下げた
- **boid を Cloudflare の Worker にする**: boid の価値は手元の実行環境(コンテナ、workspace の永続化)にあり、Worker にはできない
- **業務コンテナを boid の job として動かす**: 業務コンテナは常駐して API を出すもので、使い捨ての job とは形が違う。顧客の AKS では boid がない。独立したコンテナにする

## 未決

1. Durable Object の WebSocket(ハイバネーション)で、大きいボディ(スクリーンショット・ダウンロードしたファイル)をどこまで中継できるか。上限を超えるものの返し方。**段階 1 では、要求も答えも 8 MiB までにした**(base64 の JSON のフレーム)。超えるものは、手元に置いて ID で取らせる
2. 同じ接続先に複数のインスタンス(Pod のレプリカ)がつないだときの扱い(1 つだけ許すか、振り分けるか)。**段階 1 では、新しい接続が古い接続を置き換える**(再起動した手元が、古いソケットの切断を待たずに済む)
3. 非同期の API の約束(job の投げ方、状態の名前、結果の取り方)を、業務コンテナと boid で共通の形にするか。共通にするなら、どこに書くか
4. エージェント向けの説明の形(自由な文か、OpenAPI のような決まった形か)と、エージェントへの見せ方(`list_credentials` に足すか、別のツールにするか)。**段階 1 では、自由な文(8000 文字まで)を `hello` で送り、`list_credentials` に出す**
5. 呼び返しをサービス単位より細かく絞りたくなったとき、0008 の口の照合を使い回すか

## 改訂(2026-11-23): 使い道を業務コンテナに広げ、所有者の決まった接続にする

- 案は boid を接続先にすることが出発点で、決定 1 を「boid を `identity` の接続先にし、最初は Cloudflare Tunnel で公開する」、トンネルを構想の決定 2 にしていた
- 業務特化のコンテナ(Playwright でレガシーシステムを操作する、将来は顧客の AKS で本番の調査をする)という使い道が増え、トンネルが本命になった。Tunnel の段階を飛ばし、最初からトンネルで作る
- 手元からゲートウェイを呼び返す道を足した(決定 5)。提供元のカスタムコネクタがないハーネスで、全部のサービスに届くトークンを手元に置かないため
- 呼び返しには「誰として」が要る。依頼ごとの委任も検討したが、複雑さに見合わないので、接続ごとに所有者を決める形にした(決定 2、代案の 1 つめ)。それに合わせて、登録を管理者からペアリングに(決定 3)、証明をシークレットから鍵ペアと接続のセッションに(決定 4)変えた
- 案の未決のうち、資格の形(→ 決定 3・4)と、ユーザーごとかデプロイで 1 つか(→ 決定 2)を閉じた。長いリクエストの中継は、非同期をサービスの側の約束にすること(→ 決定 6)で、ゲートウェイの課題ではなくした

## 実装のメモ(2026-11-23)

- 所有者の付け替え(決定の「管理者は所有者を付け替えられる」)は、まだ作っていない。いまの管理者の画面(`/admin/local-services`)は一覧と取り消しだけで、所有者が退職したときは取り消して、新しい所有者がペアリングし直す。付け替えると呼び返しが新しい所有者の権限で動くので、付け替えのときに呼び返しの選択を空にする形で、要るようになったら足す
- 所有者のローカルサービスの一覧は、ホーム(つないだサービスの画面)の節と、サービスごとの設定(`/local-services/<ID>`)に置いた
- 同じ所有者が同じ名前でペアリングし直すと、確認のチェックを入れたときだけ置き換える(ID は引き継ぎ、呼び返しの選択は選び直す)

## 名前(2026-11-24)

- 仕組みを「トンネル」、つないだものを「ローカルサービス」と呼ぶ(直樹)。案と実装の最初の版では「逆向きの接続」「手元のサービス」と呼んでいて、伝わりにくかった。この ADR の本文も新しい名前に直した
- コードも合わせた: URL は `/tunnel/...`、接続の ID は `tunnel:<ID>`、Durable Object は `TunnelConnection`(binding `TUNNEL`、migration `v4` で `ReverseConnection` から名前を変えた)、設定は `TUNNEL_PAIRING` / `TUNNEL_CALLBACK`。Registry の保存のキーだけは、登録を残すために `reverse:` のまま
- 「Cloudflare Tunnel」(代案で取り下げたもの)とは別物。紛らわしいところでは、Cloudflare Tunnel と必ず書く
