# 0008 アプリには、使える口を絞った許可を出す

- 状態: 案(2026-11-11、直樹とのディスカッション)。未実装
- 関連: [concept.md](../concept.md)(「ゲートウェイがやらないこと」のメソッドやパスによる認可)、[auth-design.md](../auth-design.md)、[0004](0004-one-deployment-per-organization.md)(1 つのデプロイ = 1 つの組織)、[0005](0005-murmur-as-a-feature.md)(機能の口。読める口は入口が固定する)、[background-access.md](../background-access.md)、Murmur の [`0022`](../../murmur/docs/adr/0022-murmur-federation.md)(組織の管理者から見た情報の脱出口)・[`0024`](../../murmur/docs/adr/0024-connectors-own-webhooks.md)(購読の管理)
- 発端: novshi-tech/heddleway-calendar の `docs/adr/0001`(複数のデプロイのカレンダーを同期するツール。この許可が前提条件)

## 背景

いま Heddleway に OAuth でつなげるクライアントは、実質スタンド(Claude、ChatGPT)だけ。スコープは `gateway` の 1 つで、許可されたクライアントは、本人がつないだどのサービスにも、どのメソッドとパスでも届く。スタンドは人の代理で何でもするので、これで合っている。

一方で、スタンドではないものをつなぎたい場面が出てきた。

- エージェントは万能だが、動かすたびにコストがかかり、結果が揺らぐ。動いているときしか働かない。決まった処理を、人がいないときにも、毎回同じ動きで回したいものがある(カレンダーの同期、決まった箱の見張り、集計)
- そういう小さい自動化ツールに、今の許可は広すぎる。カレンダーを同期するだけのツールが、メールにも会計にも届くリフレッシュトークンを預かることになる
- 組織の管理者から見ると、何にでも届くクライアントが外に増えるのは、情報の脱出口になる(Murmur の 0022)

同じ問題は、Murmur を内蔵したときに 1 度解いている(0005)。中核は Murmur にトークンを渡さず、「この人の接続で、この口だけを読む」関数を渡す。読める口(メソッドとパスの組)は入口が固定し、本人が有効にするまで何も読めない。これを、Worker の外のクライアントにも出す。

## 言葉

- **スタンド**: 人の代理で動くエージェントのクライアント(Claude、ChatGPT)。今までどおり `gateway` のスコープで、本人のすべての接続に届く
- **アプリ**: スタンドではないクライアント。決まった処理をするツール。使える口を絞った許可で届く。画面の「アクセスを許可したアプリ」の一覧には、今までどおりスタンドも並ぶ
- **口**: サービス・メソッド・パスの組。Murmur の「読める口」と同じもの。アプリの口には書き込みも入るので、「使える口」と呼ぶ

## 決定(案)

### 1. アプリは、管理者がデプロイに登録する

- 管理者が管理画面で、アプリを登録する。登録するのは、名前、クライアント ID(メタデータ文書の URL)、説明(同意の画面に出す文)、使える口の一覧
- 使える口の一覧は、アプリの側が定義の形で配り、管理者が読んで登録する。接続先の定義やプラグインの登録と同じ流れ
- 登録されていないクライアントは、今までどおり `gateway` のスコープしか頼めない。絞った許可を受けられるのは、登録されたアプリだけ
- 管理者が扱うのはアプリの定義だけ。ほかのユーザーの認証情報には、相変わらず触れない

これで「どのアプリが、この組織のどの口に届くか」を、組織の管理者が決められる。

### 2. 使える口は、サービス・メソッド・パスで決める

サービスの単位だけでは足りない。Microsoft 365 は 1 つのサービス(`graph`)にメールも予定表もファイルも入っているので、「カレンダーだけ」をサービスでは切れない。

- 口は「サービス、メソッド、パスの正規表現」の組の一覧。照合はパス(クエリの前)だけで行う。Murmur の読める口と同じ形で、同じ照合を使う
- 一覧にない呼び出しは、上流に送る前に断る
- ボディの中身は今までどおり見ない(条件・リスクの 2)

concept.md の「メソッドやパスによる認可はしない」は、スタンドについてはそのまま。アプリについては「登録された口だけを通す」に改める。ゲートウェイが API の仕様を知らないことは変わらない(口の一覧は、アプリの定義が持ってくる)。

### 3. 本人が、アプリごとに同意する

- アプリは OAuth の認可で、スコープ `app:<名前>` を頼む。クライアント ID が登録と合わなければ断る
- 同意の画面には、登録された説明と、届くサービスを出す(「このアプリは、Google Calendar と Microsoft 365 の予定表だけを読み書きします」)。スタンドの同意の画面(「あなたがつないだサービスの API を呼び出せるようになります」)とは文言を分ける
- 許可は本人のもの。管理者が登録しても、本人が同意するまでアプリは何も呼べない。本人は「アクセスを許可したアプリ」の一覧から取り消せる
- 管理者がアプリの登録を消すと、そのアプリの許可はすべて使えなくなる

### 4. 許可に絞りを持たせ、中継で確かめる

- 許可(grant)に、アプリの名前を持たせる。`list_credentials` は、そのアプリの口にあるサービスの認証情報だけを返す。`issue_token` は、それ以外の認証情報を断り、発行するトークンにアプリの名前を入れる
- 中継(`/api/<service>/...`、`api_get`・`api_request`)は、トークンにアプリの名前があれば、呼び出しが口の一覧にあることを確かめる。一覧は呼び出しのたびに登録から引く(登録を狭めたら、すぐ効く)
- 機能(トピック索引)には、口の一覧に載せない限り届かない
- 操作ログに、アプリの名前を足す

### 5. 入口は増やさない

- アプリも、スタンドと同じ入口でつなぐ(OAuth の認可、MCP の `list_credentials`・`issue_token`、REST の中継)。アプリのための別の API は作らない
- 人がいないときに動くのは、リフレッシュトークンで足りる(使わない期間が 30 日を超えると切れる)。上流の接続のつなぎ直しが要るときは、中継がそう返すので、アプリが本人に知らせる
- 管理者が登録する `client_credentials` の接続先(background-access.md)は、今までどおり同じ Worker の機能だけのもの。アプリには出さない。アプリが使うのは、いつも本人の接続

### 6. Heddleway は Webhook の受け口を持たない

- 上流の通知(Graph のサブスクリプション、Google の通知チャネルなど)が要るアプリは、中継を通して購読を作り、通知の宛先を自分の URL にする。購読の更新と後始末もアプリがする
- 購読を作る・消す口は、アプリの使える口の一覧に入れる
- 同じ Worker の機能(トピック索引)の Webhook は、今までどおり機能の経路(`/murmur/...`)で受ける。これは機能のもので、中核の受け口ではない

## 影響

- スタンドには何も変わらない。スコープ `gateway` と今の同意の画面のまま
- **heddleway-calendar** がこの上の最初のアプリになる。口はカレンダーの予定の読み書きと購読だけ
- 組織の自社の業務ツールも、同じ形でつなげる。たとえば、業務ツールが本人の接続で会計サービスの決まった口だけを呼ぶ。今はスタンドがスキルで仲立ちしている処理のうち、判断の要らないものを移せる
- 権限を絞ったエージェントにも使える。定期実行のエージェントや、任せきれないクライアントを、アプリとして登録して口を絞る
- **エージェントを起こす側**もアプリにできる。たとえば、トピック索引の決まったリスト(エージェント用のタスクのリスト)を `since` で見張り、タスクが増えたらエージェントを起動するアプリ(Claude Code の scheduled task の `/fire` を呼ぶ、など)。トピック索引の本体は何も実行せず、参加者に通知もしない(Murmur の `0012`・`0013`)ので、きっかけを受けてエージェントを起こす部分は外に置く。口は「トピック索引の、そのリストのスレッドの読み取り」と「起動の API の呼び出し」だけで足りる。起動の API の認証情報(scheduled task のトークン)を接続先としてゲートウェイに登録すれば、アプリは秘密を持たない。アプリは次の一手を決めないので、トピック索引には書かない(Murmur の `0032` の決定 1)。起こされたエージェントが、本人の代理として経過を綴じる
- 複数のデプロイにつなぐアプリ(heddleway-calendar)は、組織をまたいでデータを運べる。0004 の決定 4(組織をまたいで書くときはユーザーに確認する)はスタンドの約束で、アプリには届かない。代わりに、それぞれの組織の管理者がアプリを登録することが、その組織としての了承になる。何を運ぶかは、アプリの定義と説明に書く

## 条件・リスク

1. **絞れるのは口まで。** 口の中で何をするかは、アプリの規律になる。カレンダーの口を許されたアプリは、予定の中身も読める。「時間帯しか写さない」をゲートウェイは強制しない。管理者は、アプリの定義とコードを見て登録する
2. **ボディで対象が決まる API は、パスでは絞れない。** Graph のサブスクリプションは、購読する対象(`resource`)がボディにある。`POST /subscriptions` を許すと、アプリは予定表でなくメールの購読も作れる(届くのは変更の通知で、本文ではないが、漏れではある)。未決 1
3. 正規表現の書き間違いで、口が広くなる。照合は全体一致にし、アプリの定義にテスト用の例(通る呼び出し・通らない呼び出し)を付けられるようにする
4. 上流の権限(OAuth のスコープ)は、サービスの接続で決まったままで、アプリごとには狭まらない。狭めるのは中継だけ

## 代案

- **サービスの単位で絞る**(同意の画面でサービスを選ぶ): 作りは一番軽い。Microsoft 365 が 1 つのサービスなので、カレンダーだけに絞れない。採らない
- **アプリが自分の口を名乗り、本人の同意だけで通す**(管理者の登録なし。メタデータ文書に口の一覧を書く): 手軽だが、本人がパスの一覧を見て判断することはできず、組織の管理者も止められない。採らない
- **上流の側で、権限を絞った接続を別に登録する**(concept.md の今の答え): 1 人が 1 つのサービスにつなげる接続は 1 つ(0004 の決定 5)。Google は API ごとにサービスが分かれているのでこれで足りるが、Graph は足りない
- **アプリを Worker の機能として内蔵する**(Murmur と同じ): 口の絞りは今の仕組みで足りる。ただし機能は 1 つのデプロイの中でしか動かないので、複数のデプロイにまたがるものは作れない。少数の人のための機能が中核のリポジトリに入る

## 未決

1. Graph のサブスクリプションの対象を絞るか。案は 3 つ: (a) 絞らず、リスクとして定義に書く、(b) 口の定義に「ボディのこの項目がこの形」という条件を足す(ボディを見ない原則の例外になる)、(c) 購読だけはゲートウェイが代わりに作る
2. 口の定義の形(JSON)と、配り方。プラグインの登録と同じように、リポジトリの URL から読むか
3. Murmur の読める口(`murmur/src/ports/gateway.ts` の `ReadScope` と `inScope`)を中核に移して、機能とアプリで同じ型を使うか
4. アプリが MCP を話さずに済むよう、OAuth のアクセストークンで直接 REST を呼べるようにするか。入口を増やさない(決定 5)ことと引き換えになる
5. 使わない期間が 30 日で切れる許可を、アプリには長くするか。切れたときに、人がいないときに動くアプリが、本人にどう知らせるか
6. 口がユーザーごとに違うときをどう書くか。口の一覧はアプリの定義(全員に共通)だが、絞りたい対象がユーザーごとに違うことがある。たとえば Google Tasks の「本人のエージェント用のリストだけ」は、パスにリストの ID が入る(`/tasks/v1/lists/{リストの ID}/tasks`)ので、正規表現の 1 つの一覧では書けない。案は (a) リスト単位では絞らず、サービスとメソッドまでにする、(b) 口の定義に本人が同意のときに選ぶ値(リストの ID など)を置けるようにする、(c) トピック索引の読み取りを通し、リストの選択はトピック索引の側の接続に任せる。トピック索引の読める口(未決 3)でも同じ問いになる
