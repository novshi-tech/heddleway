# 0047 API の一覧・詳細・操作も、投影の全件ではなく要る範囲だけを読む

- 状態: 採用（2026-11-18、直樹）。進める順番の 1〜4 を実装した（末尾の「実装の記録」）。5（実データで確かめる）はデプロイのあと
- 関連: 0014（fold は 1 段・リンク先の状態はクエリ層で合わせる・結び候補）、0021（D1）、0030（クエリ層の解決）、0033（リンクの可視性）、0038（担当と名指し）、0046（取り込みの作業範囲）、H1・H3・H8

## 背景

0046 で、取り込みと期限の見回りは投影の全件を読まなくなった。残ったのは API の経路（スタンドが呼ぶ一覧・詳細・操作）で、どれも `MurmurService.state()` で投影の全件（スレッドとシグナル）を読み、コアの関数に丸ごと渡している。isolate の写し（0046 の背景）が温まっていれば読む行はほぼないが、API の呼び出しは冷えた isolate に当たりやすく、そのたびに全件を読む。

あるデプロイ（スレッド 440 本・シグナル 860 通ほど）で、エージェントが 1 時間ほどの作業（トピックの詳細を 30 回、送信の記録を 10 回、アテンションを外すのを 6 回など）をしただけで、D1 の rows_read が 1 時間 7 万行になった。冷えた isolate に当たった 1 回あたり、全件の 1,400 行を読んでいる。量はデータに比例して増え続ける（0046 の背景と同じ）。

それぞれの経路が実際に見ているのは一部である。

| 経路 | 見ているもの | 今の読み方 |
| --- | --- | --- |
| 詳細（`getThreadView`） | そのスレッド、見える結んだ先のスレッドとそのシグナル（タイムライン）、結び候補 | 全件。結び候補（`linkCandidates`）は、見える全スレッドのアンカーのキー（`crossKeys`）を総当たりで比べる |
| 一覧（`listThreads`） | 見えるリストのスレッド、それぞれの結んだ先（最新の更新・担当・名指し・結んだ先の様子）、結び候補 | 全件。結び候補のために全シグナルのアンカーを読み、スレッドごとに総当たりする（スレッド数の 2 乗） |
| 操作（片付け・再開・メモ・担当・アテンションを外す・結ぶ・外す・移す） | ID で決まるスレッド 1〜2 本とそのシグナル | 全件。結果に詳細を返すので、もう 1 回全件を読む |
| 送信の記録（`recordSent`） | 送信の ID（`sentRef`）とアンカーを索引で引いたシグナルとスレッド、返事の置き先・元のスレッド | 全件（もう 1 回、詳細のために全件） |
| まとめて外す（`acknowledgeMany`） | ID で決まるスレッド | 全件 |
| 未解決のアドレス（`unresolvedAddresses`） | 見えるシグナルのアドレスのうち、Contact に解決できないもの | 全件（シグナルを全部なめる） |

## 決定（案）

### 1. 経路ごとに範囲の意味を純関数で決め、保存先はそれを引く（0046 の決定 1 と同じ形）

コアの判断の関数（`getThreadView`・`listThreads`・`commands.ts`・`outbound.ts`）は、受け取った投影の中だけで決める今の形のままにする。シェルが経路ごとの範囲（部分的な `Projections`）を組み立てて渡す。範囲の意味は経路ごとの純関数（`selectThreadScope`・`selectListScope` など）で書き、メモリの保存先はそれをそのまま使い、D1 は SQL で同じものを引く。両者の一致は、0046 と同じく全シナリオの全スレッドで確かめる。

- **詳細**: そのスレッド、`links` のスレッド、それらの全シグナル、結び候補（決定 3）
- **操作**: 対象のスレッド（移すなら移し先も、結ぶなら相手も）、それらの全シグナル、対象のシグナル。操作のあとの詳細は、操作で畳んだ範囲に結び候補を足して作る（全件を読み直さない）
- **送信の記録**: 0046 の `threadingRequest` と同じ索引の引き方（`sentRef` の messageId、アンカー）に、返事の置き先（`reply_to_thread_id`）と元のスレッド（`source_thread_id`）を足す
- **一覧**: 決定 2

### 2. 一覧は、見えるリストのスレッドの行だけを読み、シグナルを読まない

- 見えるリスト（Viewer の読者になっているデータソース）のスレッドを、`data_source_id` で引く。`open` 系の絞り込み（`open`・`my_turn`・`triage`・`awaiting`・`overdue`）は、開いている（片付けておらず、ソースで完了していない）スレッドだけ読めば足りるので、`threads` に `is_open` の列を足して絞る。`all` と `mine` は閉じたものも読む
- 結んだ先のスレッドは、`links` の ID で引く（見える範囲の外なら出さない。0033）
- 一覧の項目の計算から、シグナルへの参照をなくす。`linkedActiveSinceDismissed` は結んだ先のシグナルの時刻を見ているが、同じ時刻はスレッドのログ（`log` のシグナルの項目の `at`）にある。ログで見るように書き換える（結果は同じ。H1 のシナリオで確かめる）
- 結び候補は決定 3 の索引で、一覧のスレッドのキーとまとめて引く

`my_turn` は担当とアテンション（0038）で決まり、マスタ（読者・アドレス）に依存するので、列だけでは絞れない。開いているスレッドの全部（見えるリストの中）を読み、コアが今までどおり決める。

### 3. 結び候補はキーの索引で引く

- `thread_keys(key, thread_id, data_source_id)` を足す。スレッドのアンカーのキー（`crossKeys`: ソースの区切り・`msg:<Message-ID>`・Jira キー・PR）を、スレッドを保存するたびに入れ替える（0046 の `thread_named` と同じ扱い。投影からいつでも作り直せる）
- 結び候補は、対象のスレッドのキーで `thread_keys` を引き、見えるリストのスレッドだけ残す。候補のスレッドは件名と ID しか使わないので、行だけ読む（シグナルは読まない）
- コアの `linkCandidates` は今、候補のスレッドのキーをシグナルから作る（`crossKeys(p, u)`）。範囲にキーの表を添えて渡し、そこから引く形にする（キーの表が添えられていなければ、今のとおりシグナルから作る。メモリの保存先とテストは今の形で通る）

### 4. 未解決のアドレスは、範囲を絞らずに今のまま全件（isolate の写し）を使う

名寄せのときにしか呼ばない。アドレスの索引を足すほどの頻度ではない。

### 5. isolate の写しは残す

範囲で読むようになっても、温まった isolate では写しがいちばん安い。写しがあれば写しから範囲を選び（`select…Scope` を写しに当てる）、なければ D1 から範囲を引く。写しの凍結（0046）の CPU は、写しを作るとき（全件を読んだとき・全件を保存したとき）にしかかからない。

## 代案

- **写し（isolate のキャッシュ）だけで済ませる**: 冷えた isolate に当たると全件を読む。API の呼び出しはまとまって来ないので、写しが温まっている見込みは取り込みより低い
- **一覧を `my_turn` などの列で絞る**: 担当とアテンションはマスタ（読者・アドレス・Contact）に依存するので（0030・0038）、fold が持てる列は上位集合までになる（0046 の `named_pending` と同じ）。開いているスレッドだけで十分小さくなるうちは、足さない（未決 1）
- **一覧から結び候補を外す**: API の形が変わる。スキルは詳細の結び候補を主に使うが、一覧でも見ている。索引で安く出せるので外さない
- **Durable Object に移す**（0021 のもう 1 つの候補）: 0046 の代案と同じ理由で、先に範囲で読む形にする

## 帰結

- 詳細と操作で読む行は、そのスレッドと結んだ先とそれらのシグナル（多くて数十行）と、結び候補の行になる。今は 1 回 1,400 行（データに比例）
- 一覧で読む行は、見えるリストの開いているスレッドの行（シグナルを読まない）。全シグナル（今はスレッドの 2 倍ほど）を読まなくなる。一覧の結び候補の総当たり（スレッド数の 2 乗の CPU）もなくなる
- 範囲がクエリ層の関数の見るものを全部含むことは、シェルの責任になる。足りなければ例外ではなく「見えない」「候補がない」になって気づきにくいので、全シナリオで「範囲で作った詳細・一覧と、全件で作った詳細・一覧が同じ」を確かめるテストを足す（H1・H3・H8）
- マイグレーションが要る（`threads.is_open`、`thread_keys`。投影なので既存の行から埋める）

## 進める順番

1. 詳細と操作（決定 1。結び候補は今のまま全件から作り、範囲の行は ID で引く）。操作のあとの詳細を、畳んだ範囲から作る
2. 結び候補の索引（決定 3）。詳細の結び候補をこれに替える
3. 一覧（決定 2）。`is_open` の列、`linkedActiveSinceDismissed` のログへの書き換え、結び候補をまとめて引く
4. 送信の記録（決定 1）
5. 実データで rows_read を確かめる

## 未決

1. 一覧の `my_turn` を、開いているスレッドより狭い上位集合（名指しの残るアドレス・担当する操作の User・状態を持つソースの holders）で絞るか。開いているスレッドの数を見て決める
2. 一覧のページング（件数の上限）。今は見えるものを全部返す
3. 写しを残すか（決定 5）。範囲で読むようになったあとの、写しの命中率と CPU を見て決める

## 実装の記録（2026-11-18）

- **進め方**: 進める順番の 1（詳細と操作）と 2（結び候補の索引）は、詳細の結び候補が全件のままだと詳細が軽くならないので、まとめて入れた。3（一覧）と 4（送信の記録）も同じ変更で入れた
- **範囲の意味**: `src/domain/scope.ts` の `selectThreadScope`（詳細と操作。主なスレッド・結んだ先・結び候補と、それらのシグナル）と `selectListScope`（一覧。見えるリストのスレッドの行、結んだ先、結び候補の行と、キー）。メモリの保存先はこれを使い、D1 は `threadScope`・`listScope` で同じものを引く
- **コアの変更は 2 つだけ**: (1) `crossKeys` は、範囲に添えたキー（`Projections.keys`。fold は作らない）があればそれを使い、なければ今のとおりシグナルから作る（`crossKeysOfSignals`）。(2) `linkedActiveSinceDismissed` は、結んだ先のシグナルの時刻をスレッドのログで見る（シグナルのログの `at` は同じ時刻）
- **キーの索引**（`thread_keys`）: 保存先が、変わったスレッドの行をシグナルから作り直す。範囲にそのスレッドのシグナルがなければ書けないので例外にする（範囲はどれもスレッドのシグナルを全部含む）。期限の見回りの範囲（0046）は、期限超過を畳むとスレッドを保存し直すので、シグナルも読むようにした
- **送信の記録**: 取り込みの `threadingRequest` で、送信の ID とアンカー（タスクのときの課題キーも）を引いた範囲と、返事の置き先・元のスレッドの範囲を合わせる。2 つの lastSeq が違えば全件
- **操作のあとの詳細**: 「操作で畳んだ範囲から作る」とした決定 1 の一文は、詳細の範囲（結んだ先・結び候補）を別にもう 1 回引く形にした（範囲で読むので安い。操作の範囲を詳細の分まで広げずに済む）
- **一覧の絞り込み**: `open`・`my_turn`・`triage`・`awaiting`・`overdue` は開いているスレッド（`is_open`）だけ、`all`・`mine` は全部
- **マイグレーション**: `drizzle/0006_query_scopes.sql`。`is_open` を埋め、キーの索引は消してから入れ直す（結び候補そのものなので、余分な行を残さない。何度流しても同じ）
- **テスト**: `test/domain/scope.test.ts`（全シナリオ・全 User・全スレッド・全部の絞り込みで、範囲で作った詳細・一覧が全件で作ったものと同じ）、`test/shell/working-set.test.ts`（D1 の `threadScope`・`listScope` が純関数と同じ。冷えた isolate で詳細・一覧・アテンションを外す・メモ・送信の記録のどれでも threads と signals の全件の select がない）、`test/shell/signal-keys.test.ts`（`thread_keys`・`is_open` が差分の保存・作り直し・マイグレーションで fold と一致）。メモリの保存先が範囲を使うので、既存の API とシナリオのテストは全部この経路を通る
