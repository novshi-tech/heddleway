# 0016 次の段階: 実際のチームの実データで Ingest が使えるかを確かめる

- 状態: 採用（方向と順番。2026-10-21、直樹）。最初のデータソースはメール（Outlook）（2026-10-22、直樹。0019）。ゴールの数字は案で、段階 5 に入る前に直樹と決める。
  2026-10-23: 0020（チーム単位でセルフホストする）に合わせて、特定の会社の事情を外した汎用の書き方に直した（直樹）。個別の事情（どの会社のアカウントで回すかなど）は ADR に書かない
- 関連: `docs/retrospective-v2.md`（4 章の持ち越し 1〜6。7 はやらない）、0007（読み取り専用の実コネクタで Ingest から始める）、0015（手元の pull スクリプトの案）、0006（act-as）、0012（本体は外に書かない）、0014、0018・0020（1 デプロイ = 1 チーム）、0021（マルチテナントを外す、ストレージ）、H6

## 背景

計画 v2 で、スレッドとリンクのデータモデルとアーキテクチャは外部接続なしで成立した（`docs/retrospective-v2.md`）。
ただし Ingest の数字（H6 の 34/34）は Claude が書いたシナリオの数字で、設計メモの未決のうち「無視の閾値と監査」（判定 7）と「観測者としての Ingest だけで価値が出るか」（判定 10）は、実データでしか答えが出ない。

直樹の方針（2026-10-21）: 次は実コネクタを作り、実際のチームでの Ingest がうまく動くかを確かめる。そのために必要なことを、振り返りの持ち越しの順番でやっていく。

## ゴール

**実際のチームの連絡を読み取り専用で Murmur に取り込み続け、区切りと「返事や対応を求めているか」が業務で使える精度かを、人の訂正を正解の代わりにして測る。**

この段階が終わったときに答えが出ているもの:

1. 実データでの Ingest の精度。訂正（シグナルの移し替え、「求めているか」の直し）の件数を、取り込んだ件数で割ったもの（判定 7）
2. 観測者としての Ingest だけで価値が出るか（判定 10）。実際に使った人の判断で、続けて使いたいか
3. 運用の約束（追いたい件はスタンド経由で送って記録する）が守られているか。計画 v2 の前提の指標（どこにも結ばれなかった観測された送信、元のスレッドへのリンクのない Jira の課題、誰も持たないまま古くなったスレッド）の件数（判定 6）
4. プロンプトかモデルを変えたとき、貯めた実データを手元で再生して比べられること

完了条件（案。段階 5 に入る前に直樹と決める）:

- 試用するチームのデータソース 1 つ以上を、2 週間続けて取り込めた（本体は外に書かず、資格情報は読み取りの権限だけ）
- その期間の取り込み件数・AI を呼んだ件数・区切りの根拠の内訳・訂正の件数・前提の指標を集計した
- 1〜3 の答えを `docs/` に書き、直樹のレビューを通った

やらないこと: 性能の作り込み（0007「量の見通し」は詰まり具合を見て考える。ただし投影の差分化は 0021 で前倒しする）、本物のデータソースへの書き込み、ほかのチームへの配布（セルフホストの手順を整えるのは 0021）。

## 段階 5 に入る前に決めること

- **最初のデータソース**: **メール（Outlook）から始める（2026-10-22、直樹）。** pull で過去の分も取れ、自分の送信も観測できるので軽い。0007 は「メールボックス 1 つ、ラベルかフォルダ 1 つから」。
  LINE 公式アカウントは、チャネルを Murmur の手前の別システムが持つ形にした（0019）ので、その受け口ができるまで取り込めない。
  チーム全体をシミュレートするには LINE と Jira が要るので、メールのあと早めに入れる（直樹）
- **試用の単位**: 1 デプロイ = 1 チーム（0020）。試用するチームのゲートウェイと Murmur を 1 組立て、そのチームのスタンド（Claude のアカウント）からつなぐ。
  Murmur の User はゲートウェイのサインインの ID と 1 対 1（0003）なので、サインインできるのはそのゲートウェイの IdP のアカウントを持つ人。試用はそれで足りる。
  1 人が複数のチームに属する場合は、チームごとのスタンドでそれぞれの Murmur を巡回する（0018・0020）
- **取り込みの経路**: 手元の pull スクリプト（0015 の案。本体もゲートウェイもほぼ変えない）か、ゲートウェイに act-as を足して Worker の Cron で取る（0006。本番に近いが重い）。LINE は webhook なので受け口が要る（0019: Murmur の手前の別システム）。
  act-as は、個人の Murmur に要約を入れる経路（0022 の論点 1）とも同じ仕組みになる
- **取り込みに使う資格情報の置き場所**: ゲートウェイの資格情報はサインインしたユーザーごとに登録され、組織（チーム）の資格情報を置く場所がない。
  Murmur の側は `CredentialRef`（principal が user か organization。`gatewayCredentialId` は未使用）で「このデータソースはどの資格情報で取るか」を持つが、本体からゲートウェイを呼ぶ経路（0006 の ServiceClient・act-as）がない。
  共有のデータソース（チームの LINE 公式アカウントや共有のメールボックス）はチームの資格情報で取る約束（0013）なので、チームの資格情報をゲートウェイのどこに置くかを決める
- **実データの本文を Claude に送る範囲と、記録（`recordings`）の置き場所**（0007「量の見通し」の 6。0015 の案は手元だけ、git にも DB にも入れない）
- **完了条件の数字**（期間・件数）

## 代案

- いきなり 5 から始める: 1〜3 がないと、宛先を推測した記録や、件名の読みにくさ、スタンドの説明の誤りが訂正の件数に混ざり、Ingest の精度と切り分けられない
- 実データの代わりにシナリオを増やす: Claude が書くシナリオでは、判定 7・10 に答えが出ない（v2 の振り返りの結論）
